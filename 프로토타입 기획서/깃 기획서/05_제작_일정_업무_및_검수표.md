# wayMate 제작 일정·업무 및 검수표

> 2026-11-11 구현 상태: my_trip 공통 JSON·최소 서버·웹 저장·실제 차량 제한 확인·HTTP 이어받기/ACK를 구현했다. [07 실행·지원 범위](07_첫_전달_실행_및_계약.md)를 참고한다. 아래 전체 설계·W/Q/V 조건의 완료를 뜻하지 않으며 상대 연결·음성·내비·O01·RESET은 후속이다.

작성일 2026년 11월 11일 · 버전 0.6 · 팀 공유용 수정안

대화형 온보딩에서 시작해 에이전트 추천, 모바일·차량 이어받기, 선택형 차량 대화, 짧은 만남, 두 가지 여행 결말을 제작한다. 작업 순서는 **공통 기준·환경 준비 → 실제 정보 전달 한 건 확인 → 기능 제작·연결 → 통합 검수 → 시연본 고정**으로 관리한다. SDK의 가능 여부는 별도 작은 시험으로 일찍 확인한다.

기준은 [01. 제작 범위](01_목업_기획_범위_정의서.md), [02. 시연 시나리오·대본](02_시연_시나리오_및_대본.md), [03. 화면·상호작용](03_화면_및_상호작용_설계서.md), [04. 개발·연동 계약](04_개발_및_연동_명세서.md)의 v0.6다. `W`는 작업, `G`는 마일스톤, `Q`는 기능 검수, `V`는 서비스 가설·실현성 검증, `I`는 확인 사항·이슈다. 기존 DM 기능·S 장면·M/P/O 화면 ID를 유지한다.

**아직 정하지 않은 담당자·검토자·가용 시간·착수일·마감일은 모두 미정이다.** 날짜 대신 선행 관계와 완료 조건을 먼저 정의한다. 작업은 확인한 부분 산출물이 있는 W02·W04를 ‘진행’, 나머지를 ‘대기’로 두며 기능 검수 결과는 ‘미실시’로 유지한다. 문서가 있다는 이유로 구현·빌드·SDK·통합 검수가 완료된 것으로 표시하지 않는다.

작성일과 이야기 속 여행일 2026년 11월 14일은 제작·제출 마감이 아니다. 기존 자료의 제작 일수는 확정 일정으로 적용하지 않는다. 실제 이름·기한·소요 시간을 확인한 항목만 이후 갱신한다. 이 문서의 역할 수를 실제 팀원 수로 해석하지 않는다.

### 1.1. 완료와 통과의 구분

| 구분 | 판단 기준 |
|---|---|
| 문서 정리 | 범위·대본·화면·개발 계약·작업표의 ID와 기준이 연결됨. 팀 검토자 배정·합의 여부와 별도로 관리 |
| W 작업 완료 | 해당 작업의 산출물·단위 확인·증빙이 있음. 아직 전체 시연 검수를 통과했다는 뜻은 아님 |
| 기능 검수 완료 | 기능별 필수 Q 분기를 대상 버전에서 확인하고 통과 증빙 등록 |
| 기본 시연 완료 | 실제 모바일 웹·전달 서버·Pleos 에뮬레이터 앱이 연결되고 필수 흐름·두 결말·적용 검수 통과 |
| 실제 SDK 완료 | 실제 추가·조회·취소·제거·중복 방지·복구의 적용 시험과 증빙이 있음. 모의 성공과 구분 |
| 최종 인계 완료 | 시연본 버전·모드·환경·실행 안내·검수·미완료 기록이 일치하고 리허설 확인 |

필수는 DM01~DM09·DM11, S01~S12, M01~M04·P01~P04·O01이다. DM07의 일반 통화 UI·샘플은 필수지만 MC 샘플은 추가다. DM10·S13·P05 후기·장식, 선택 이유 입력도 추가다. 실제 매칭·생성형 대화·성향 추론·실시간 통화·음성 특징 분석을 제작 완료 조건에 새로 넣지 않는다.

DM06은 서로 알아가고 스몰토크를 돕는 콘텐츠 경험이며 현재 목록은 목업용 대표 구성이다. 밸런스 게임은 기획 확장 예시로 반영하되 제작 채택은 미정이다. 새 작업·필수 완료 조건·시연 시간을 자동 추가하지 않고, 채택 시 범위·대본·API·검수·일정 영향을 함께 정한다. ‘복귀’는 대표 이야기의 숙소 도착이고 제작 마감과는 무관하다.

02번의 발표 목표는 **대표 약 8분 + 다른 결말 약 60초**다. 장면 합계 460초에 기기 전환·설명을 더한 기준이며 개발 소요 시간이 아니다. MC 약 30초·후기 약 20초는 채택 시 별도로 더하고, 실제 시간은 리허설 후 기록한다.

### 1.2. 상태 기록

- 작업 상태: `대기 / 진행 / 검토 / 완료 / 차단 / 보류`.
- 검수 결과: `미실시 / 통과 / 실패 / 차단`.
- 검수 적용 여부: `필수 / 조건 충족 시 필수 / 미적용`. 조건 결정 전의 실제 적용 여부는 미정으로 기록한다.
- 모드·기능 채택이 결정되지 않았다고 통과로 표시하지 않는다. 미채택 추가 기능은 결정 이후 보류·미실시로 남기며 통과 수에 넣지 않는다.
- 이미 수행한 시험은 버전·모드·결과를 보존한다. 모의 모드로 바꿨다고 이전 실제 SDK 실패를 미실시로 지우지 않는다.

## 2. 역할별 담당 업무

전체 팀은 5명이며 개발 참여 인원·역량·실제 배정은 미정이다. 역할별 소유 경로와 개발 1명/2명/3명 배치 예시, 기획서·소재·검증을 함께 진행할 방법은 [06 개발 아키텍처·분담 가이드](06_개발_아키텍처_및_분담_가이드.md)를 따른다. 이 표의 역할 수가 팀원 수나 개발자 수를 뜻하지 않는다.

### 3.1. 먼저 확인할 연결과 병행 가능한 작업

현재 확인한 부분 산출물은 저장소 구조·Git 제외 설정과 차량 mock 앱의 첫 화면 빌드·설치·실행이다. 초기 차량 실행 근거는 커밋 `4a46dfc`와 차량 README, 로컬 runtime 기록에 있다. 이에 W02·W04는 진행으로 표시한다. W02의 서버 실행·저장 기반과 W04의 실제 제한 현재값/변경·미확인 잠금은 아직 완료되지 않았고, G01·기능 Q·실제 SDK 결과를 통과로 바꾸지 않는다.

- W03~W05로 전체 화면을 완성하기 전에 웹 선택값 한 건을 실제 차량 앱에서 불러온다. 양쪽에 같은 샘플을 따로 넣는 방식으로 대신하지 않는다.
- W03·W07의 B 반응은 초기에 임시 명령으로 단위 확인할 수 있다. 이것은 O01 완성이나 전체 시연 완료와 다르다. 적용한 명령·역할·회차를 기록한다.
- W04 뒤 W06 SDK 시험을 첫 서버 연결과 병행할 수 있다. 이 시험은 별도 에뮬레이터 시험 경로의 API 가능성 확인이며 대표 시연의 전체 동의·복구 검수를 대신하지 않는다.
- W08과 W09는 W01의 같은 대본·소재 ID를 사용해 서로 병행할 수 있다. 웹·차량 복사와 실제 재생은 W10·W11·W14에서 연결한다.
- W10·W11·W12는 공통 API가 준비되면 역할에 따라 병행할 수 있다. 실제 병행량은 배정·가용 시간 확인 후 정한다.

W06은 성공·실패·미검증과 다음 행동을 기록하면 ‘기술 판단 작업’으로 완료할 수 있다. SDK가 실패했다고 W13이 완료되는 것은 아니다. 실제 시연 모드 채택은 W13의 통합 검증 결과와 연결하고, 미검증을 성공으로 표시하지 않는다.

### 6.1. 필수·조건부 집계

기본 필수는 **Q01~Q15·Q17·Q19~Q23·Q25~Q26**이다. Q16은 최종 실제 모드, Q18은 후기, Q24는 MC, Q27은 이유 입력을 채택할 때 추가로 필수다. Q의 조건부 적용을 결정할 담당자·결정일·마감은 미정이다.

Q15·Q19·Q20의 실패·경합 계약은 fake Adapter·서버 테스트로 기본 검증한다. 실제 모드를 선택하면 실제 호출·재시작·취소·제거의 적용 분기도 실제 환경에서 확인한다. 모의 테스트만으로 Q16이나 실제 SDK 부분을 통과 처리하지 않는다.

실제 SDK를 한 번이라도 호출한 이력이 있으면 최종 모드를 모의로 바꿔도 그 작업의 정리·미확정 복구 확인은 생략할 수 없다. Q14·Q19·Q20의 해당 실제 이력 확인을 남긴다. 이것은 미완성 실제 연동 전체를 통과로 만들라는 뜻이 아니다. Q16의 실제 실패·미검증은 보존하고 기본 모의 시연의 통과 여부를 따로 판단한다.

추가 기능이 미채택으로 결정되면 해당 Q는 미적용·미실시로 남긴다. 시험 도중 실패한 뒤 기능을 보류해도 실패 이력을 삭제하지 않는다. 미정·차단·미실시를 통과처럼 집계하지 않는다.

### 6.2. 분기별 검수 실행 기록

### 6.3. 변경 후 재검수

통과 기록에는 대상 버전을 남긴다. 수정 후 영향받는 Q와 관련 분기만 재검수하고, 기존 증빙을 재사용할 때는 코드·데이터·소재·환경 중 해당 경로가 바뀌지 않았다는 근거를 기록한다. 버전만 다르게 적어 이전 통과를 복사하지 않는다.

새 APK·시연 묶음에서는 기본 실행·전달·두 결말의 확인을 다시 남긴다. 전체 부정·경합 시험을 무조건 반복하기보다 새 변경·실패·미확인 범위에 맞춰 검수한다. 추가 기능을 붙였으면 공유 통화·음성·공개·초기화·재시연에 미치는 영향도 포함한다.

## 8. 리허설·최종 시연본·인계

### 8.1. 리허설 순서

1. 04번 실행 절차로 서버·웹·O01·Pleos 앱을 시작한다. 실제 환경·버전·주소·capabilities·선택 모드와 미정리 기록을 확인한다.
2. 전체 초기화에서 필요한 웹·차량 ACK와 외부 경로 정리를 확인한다. 새 회차가 준비되기 전 진행하지 않는다.
3. S01 대화형 온보딩에서 별명·외형·표현·공개를 확인하고, S02 계획 저장 뒤 S03 자동 추천·S04 연결을 진행한다.
4. S05에서 웹 변경값을 실제 차량 앱으로 이어받고 ACK를 확인한다. 본인 모드 검수는 별도 분기로 남긴다.
5. 대표 순서로 S06 상대 캐릭터·S07 말 전달·S08 통화 샘플을 선택해 보여준다. 이 순서는 발표 예시이며 강제 단계처럼 설명하지 않는다. B 메시지는 시연 이벤트임을 구분한다.
6. S09 양쪽 경로·취향에 맞는 장소와 일정, 동일 제안 수락·운전자 승인을 확인하고 실제/모의 표시를 유지한다.
7. S10의 도착·만남 재연에서 캐릭터의 소개 표현이 실제 B 대사와 이어지는 장면을 보여준 뒤, 만남 종료·S11 선택·S12-A 함께 결말로 간다.
8. 최종 선택 재시연으로 S12-B 내 캐릭터 결말을 보여준다. 친구 대화와 다음 활동까지 확인하고 이유 입력 없이 종료한다.
9. 채택한 MC·후기는 별도 추가 장면으로 보여준다. 후기는 함께 결말을 준비한 회차에서만 S13으로 진입하며, 그 준비 시간을 후기 약 20초와 구분한다.
10. 실제 경로 이력이 있으면 종료 후 정리·관측을 남긴다. 버전·모드·실측 시연 시간·이슈·미완료 항목을 기록한다.

대표 약 8분·다른 결말 약 60초는 목표값이다. 리허설에서 실제 소요·설명/조작/기기 전환·추가 장면 시간을 나눠 기록하고 필요하면 02번의 시간표를 갱신한다. 리허설 일시·운영 담당·최종 발표 시간 제한은 미정이다.

### 8.2. 시연본 고정 체크리스트

아래는 구현 후 확인할 체크리스트다. 초기값은 모두 미확인이다.

- [ ] 코드 커밋·차량 APK·scenario/schema·manifest·문서 버전이 같은 시연본 기준으로 기록되어 있다.
- [ ] 웹/서버/O01 실행·차량 API 주소·빌드/설치·환경·실제/모의 모드와 capabilities가 일치한다.
- [ ] connected와 my_trip 전달, 일반 콘텐츠 선택·두 결말이 실제 에뮬레이터 앱에서 동작한다.
- [ ] 해당 모드의 필수 Q가 통과하고 분기별 증빙·미실시·실패·미적용이 구분되어 있다.
- [ ] 실제 SDK 미검증·실패·unknown·모의 진행이 성공으로 합쳐지지 않고 외부 정리 상태가 확인되어 있다.
- [ ] 실제 제한·비활성·보고 만료·복구에서 승인 우회·자동 SDK 재실행이 없다.
- [ ] 전체 초기화와 결말 재시연의 기록·요청·음성·장식 정리가 확인되어 있다.
- [ ] 필수 캐릭터·자막·음성·표현이 일치하고 무음·좁은 창·확대에서도 진행 가능하다.
- [ ] 추가 기능의 채택 여부·검수·소재·capabilities와 변경 영향 재검수가 일치한다.
- [ ] 필수 시연 차단 이슈가 해소되었고 남는 미완료·대체 진행·재현 방법이 적혀 있다.
- [ ] 실제 리허설 시간·운영 순서·실행물·증빙 위치를 인수자가 찾을 수 있다.
- [ ] 제출 형식·마감·제출 담당·확인자는 확인된 값만 기록되어 있다. 미확정 항목은 미정으로 남아 있다.
