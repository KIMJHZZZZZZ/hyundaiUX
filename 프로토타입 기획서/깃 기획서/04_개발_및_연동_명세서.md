# wayMate 개발 및 연동 명세서

> 2026-11-11 구현 상태: my_trip 공통 JSON·최소 서버·웹 저장·실제 차량 제한 확인·HTTP 이어받기/ACK를 구현했다. [07 실행·지원 범위](07_첫_전달_실행_및_계약.md)를 참고한다. 아래 전체 설계·W/Q/V 조건의 완료를 뜻하지 않으며 상대 연결·음성·내비·O01·RESET은 후속이다.

작성일 2026년 11월 11일 · 버전 0.6 · 팀 공유용 수정안

모바일 웹·차량 앱·시연자 패널은 시연 PC의 공통 서버를 사용한다. 서버가 프로필·공개 승인·여행·연결·요청·동의·결말의 기준 상태를 관리하고, 차량 앱은 실제 제한과 승인 조건을 다시 확인해 SDK를 호출한다. 목표 온보딩은 자유 입력·원문 저장을 실제로 연결하고, 에이전트 후속 질문·추천·캐릭터·상대 메시지·통화는 준비된 대본과 시연 데이터로 재현한다.

기준은 [01. 제작 범위](01_목업_기획_범위_정의서.md), [02. 시연 시나리오 및 대본](02_시연_시나리오_및_대본.md), [03. 화면 및 상호작용 설계서](03_화면_및_상호작용_설계서.md)의 v0.6다. **아래 모델·API·명령은 구현할 계약이다.** 현재 차량 첫 화면의 mock 빌드·에뮬레이터 실행은 [차량 앱 안내](../mock-app/vehicle/README.md)에 기록했고, 현재 서버·전달·실제 제한 읽기의 완료 범위는 07을 따르고, 아래 v3 목표·음성·SDK 계약은 구현·검증 전이다. Node 목표 버전은 `.nvmrc`의 `22.22.2`이며, 실제 실행 환경은 해당 작업에서 확인한다.

기술 용어는 아래 의미로 사용한다. 서비스 흐름·시각의 뜻은 01번, 실제 대사는 02번을 먼저 읽고 필요한 계약을 찾아보면 된다.

| 용어 | 이 문서에서의 뜻 |
|---|---|
| fixture | 인물·일정·후보·대사를 담은 고정 시연 데이터 |
| projection | 현재 역할·공개 범위에 맞춰 서버가 골라 내려주는 정보 |
| snapshot / ACK | 특정 버전의 전달 정보 / 차량이 그 정보를 확인해 서버에 알린 기록 |
| command / receipt | 저장·전송 등 행동 요청 / 서버가 해당 요청을 처리해 남긴 영수증 |
| attempt / journal | 내비 추가·제거 한 번의 시도 / 회차가 끝나도 남기는 실행·관측 기록 |
| checkpoint / finalRound | 결말 재시연용 이야기 참조 / 최종 선택 재시연의 순번 |

## 1. 구조·기술·구현 단위

### 1.1. 책임 분리

| 구성 | 기술·역할 |
|---|---|
| 모바일 M01~M04 | HTML·CSS·JavaScript ES modules. 채팅·입력·프로필·추천·연결·전달 준비 표시 |
| 시연자 O01 | 같은 서버의 별도 웹 화면. 허용된 B 응답·시간 전환·모드·초기화만 실행 |
| 전달 서버 | Node.js 22.22.2, 표준 `http`·`fs`·`crypto`. 상태 검증·명령 순차 처리·파일 저장·역할별 응답 |
| 차량 P01~P04 | Kotlin·Jetpack Compose. 공통 상태 표시, 로컬 주행 제한, 음성·내비 Adapter. P05는 추가 |

| 상태 저장 | 서버의 JSON 상태 파일과 명령 영수증, 차량의 SDK 실행 기록. 운영 계정·DB·실제 다중 사용자는 범위 밖 |
| AI·음성 | 답변·표현·소개·추천 이유·메시지·통화 샘플의 ID를 선택해 재생. 자유 추론·실제 통신 없음 |

서버는 실제 경로를 계산하지 않는다. 차량 SDK도 상대 추천이나 강릉 가상 일정의 ETA를 계산한 근거로 사용하지 않는다. 실제 내비 시험과 시연 수치는 분리한다.

### 1.2. 구현할 폴더

`mock-app/`의 기본 디렉터리와 Node 패키지 메타정보는 저장소 초기 구조에 생성했다. 아래 트리는 앞으로 구현할 상세 파일까지 포함한 계약이며, 각 API·화면·스크립트가 이미 구현됐다는 뜻은 아니다. 현재 존재하는 디렉터리와 구현 상태는 [앱 디렉터리 안내](../mock-app/README.md)를 따른다.

협업 시 구체적인 파일 소유·내부 패키지·화면/플랫폼 경계는 [06 개발 아키텍처·분담 가이드](06_개발_아키텍처_및_분담_가이드.md)를 따른다. 기존 entry 파일명과 이 문서의 API 의미는 유지한다.

```text
mock-app/

  .nvmrc
  server/main.mjs
  server/commands.mjs
  server/state.mjs
  server/projections.mjs
  server/store.mjs
  server/fixtures/gangneung-01.json
  shared/schema.json
  shared/assets-manifest.json
  web/index.html
  web/app.js
  web/operator.html
  web/operator.js
  web/views/
  web/styles.css
  assets/images/
  assets/audio/
  scripts/sync-assets.mjs
  vehicle/
    app/src/main/.../data/
    app/src/main/.../ui/
    app/src/main/.../platform/
    app/src/mock/
    app/src/real/
  tests/
  runtime/
```

`runtime/`의 상태·영수증·시험 기록과 Android 로컬 실행 기록은 버전관리에서 제외한다. 정적 서버는 `web/`과 manifest에 등록한 소재만 제공한다. `server/fixtures/`·`runtime/`·소스 전체를 웹 루트로 공개하지 않는다. 의존성·빌드 파일을 구현할 때 lockfile·Gradle Wrapper와 실제 검증 버전도 커밋한다.

차량은 `mock`·`real` 빌드 구성을 분리한다. `mock`은 실제 NaviHelper 클래스 없이도 빌드할 수 있게 하고, `real`에만 해당 SDK 의존성과 구현을 둔다. 공통 화면은 같은 Adapter 계약을 사용한다. 실제 SDK를 이용할 수 없다고 실제 모드의 성공을 모의 값으로 대신하지 않는다.

## 3. 공통 데이터 구조

### 3.1. 식별자·버전

이 문서의 목표 계약은 `schemaVersion: 3`이며 아직 구현 전이다. 현재 07의 실행 코드·JSON Schema는 `schemaVersion: 2`다. 자유 입력 payload와 기능별 음성 허용 필드는 3으로 함께 전환하며 v2로 보내거나 조용히 프리셋으로 변환하지 않는다. 날짜는 `YYYY-MM-DD`, 이야기 속 시각은 `HH:mm`, 기록 시각은 UTC ISO 8601, ID는 서버 또는 명령 발행자가 생성한 UUID를 사용한다. 아래 JSON의 짧은 ID는 가독성을 위한 예시다.

문서 버전과 API schemaVersion은 별도다. 이 문서의 schemaVersion 3를 구현 기준으로 사용하며 실제 코드·실행과의 일치는 구현 검수에서 확인한다. shareSummaryApproved는 누락 시 false, 명시한 값은 boolean만 허용한다. 공개 요약 변경도 tripVersion을 증가시킨다.

| 필드 | 형식·규칙 |
|---|---|
| `storeId` | 서버 상태 저장소 ID. 상태 파일을 새로 만든 경우 바뀜. 이전 차량 기록이 있으면 자동으로 깨끗한 상태라 간주하지 않음 |
| `runSeq`, `runId` | 전체 초기화 완료 때 증가하는 회차 번호와 새 UUID. `runSeq`는 저장소 안에서 감소·재사용하지 않음 |
| `version` | 현재 회차의 업무 상태 변경마다 증가. 단순 조회·같은 제한의 heartbeat에는 증가시키지 않음 |
| `profileVersion`, `publicationVersion`, `tripVersion` | 본인 요약, 공개 항목/승인, 여행 계획/여행 요약 공개의 별도 버전. 변경 시 이전 전달본·추천 설명 재확인 |
| `connectionVersion` | 연결 요청·수락·시간 확인·종료 변경마다 증가. 메시지 도착·heartbeat에는 증가하지 않으며 전달본 참조에 사용 |
| `commandId` | 새 사용자 행동마다 새 ID. 같은 전송의 수동 재시도는 같은 ID·같은 본문 |
| `connectionId` | 연결 한 건의 ID. 종료 후 새 연결이면 새 값 |
| `requestId` | 연결·메시지·통화·MC·만남·최종 선택의 요청별 ID. 하나의 전역 요청 ID를 공유하지 않음 |
| `proposalId` | 동일 장소·시각·체류시간 제안의 ID. 내용이 달라지면 새 값·새 동의 필요 |
| `handoffId`, `handoffVersion` | 전달 스냅샷과 버전. 단순 조회와 차량 확인 ACK 구분 |
| `finalRound` | 새 회차 0, 첫 유효한 만남 종료 때 1. 같은 이야기에서 최종 선택 재시연마다 증가 |
| `attemptId` | 내비 추가·제거 시도별 ID. SDK의 요청 ID라고 가정하지 않음 |
| `deviceId`, `vehicleSessionId`, `statusSeq` | 차량 설치·현재 실행 세션·세션 내 증가하는 보고 번호. 이전 세션·이전 번호 보고 제외 |
| `vehicleEpoch` | 같은 장치의 재접속마다 서버가 증가시키는 세션 순번. 현재 관측과 이전 세션의 늦은 보고를 구분 |
| `webClientId` | 브라우저에 보관하는 시연 웹 인스턴스 ID. 새로고침·같은 브라우저 재접속에서도 유지하며 초기화 ACK 대상 구분에만 사용 |
| `resetId` | 전체 초기화 작업 ID. 필요한 ACK를 같은 작업에 묶음 |

### 3.2. 시연 원본

서버의 fixture에 인물·승인된 B 프로필·후보·일정·장소·대본·조건별 템플릿을 저장한다. 클라이언트가 보내는 임의 점수·ETA·B 응답·만남 시각은 받지 않고 서버 원본에서 결정한다.

```json

  "scenarioId": "gangneung-01",
  "scenarioVersion": "0.5",
  "tripDate": "2026-11-14",
  "timeZone": "Asia/Seoul",
  "regionId": "gangneung-coast",
  "availability": {"A": ["13:00", "15:00"], "B": ["14:00", "15:30"]},
  "sharedWindow": ["14:00", "15:00"],
  "meeting": {
    "placeId": "fiction-cafe-01",
    "name": "바다쉼표 카페",
    "start": "14:15",
    "end": "14:35",
    "source": "fixture"
  },
  "estimates": {
    "source": "fixture",
    "etaA": "14:02", "etaB": "14:10", "etaGapMinutes": 8,

```

이 JSON은 원본의 일정 부분이다. A·B 프로필, C·D 요약, S01 질문·선택적 예시·후속 질문 cue, Q1·Q2·M1·M2·R1·R2, S08·S08-MC·S10·S12·S13의 대사·발화자·필수 공개 항목도 fixture와 manifest에 등록한다. S01 예시는 허용 답변 목록이 아니며 자유 입력 원문은 사용자 상태에 별도로 저장한다. B의 개인 일정까지 포함한 원본 전체를 `/api/scenario`로 반환하지 않는다.

availability는 만남을 잡을 수 있는 본인의 시간 범위이고 sharedWindow는 그 교집합이다. 실제 약속은 meeting.start/end, 추가 동행은 togetherActivity.start/end를 사용한다. 공통 시간이 ‘유효하다’는 것은 합의할 만남·활동이 그 범위 안에 있다는 뜻이며, 이야기 속 현재 시각이 반드시 그 범위 안이어야 한다는 뜻은 아니다. 따라서 13:50에 14:15 만남을 제안할 수 있다.

nextVisit는 연결 전부터 있던 다음 개인 일정의 도착 시각이다. returnEstimate·returnDeadline는 같은 returnPlaceId에 대한 도착 예상·마감이며, 대표 시연에서는 각자의 강릉권 숙소를 뜻한다. nextVisitLabel·returnPlaceId/Label은 본인 일정에만 포함하고 상대 projection·여행 publicSummary에는 넣지 않는다. 화면 라벨은 ‘기존 다음 일정 도착’, ‘내 숙소 도착 예상’, ‘내 숙소 도착 마감’으로 한다. 이 값들은 활동·기존 일정 이후의 고정 계획이며 실시간 교통으로 재계산한 값이 아니다.

waitAMinutes/waitBMinutes는 첫 만남 시작에서 각자의 도착 예정을 뺀 고정 대기시간이다. 장소 카드에는 본인 대기·첫 만남 20분·이후 산책 20분은 별도 선택임을 함께 표시한다. 추가 주행 7분/5분을 만남의 전체 소요나 순수 추가 부담으로 바꿔 설명하지 않는다.

storyContext.peerIntroSeen은 02번 기본 이야기에서 B가 A의 현재 승인 소개를 미리 확인하고, 당일 정차 중 A 방문 캐릭터의 소개를 들었다는 배경이다. 실제 B 기기 조회·열람·차량 ACK의 증빙이 아니다. 접점 생략 변형은 false로 두고, 누락도 false로 처리한다. 현재 공개 필드가 허용하지 않는 A 취향은 true여도 B의 만남 대사에 넣지 않는다. 이 배경은 사용자의 프로필이나 공개 동의를 변경하는 값이 아니며 별도 B 앱 구현을 요구하지 않는다.

### 3.3. 온보딩·프로필·공개 승인

| 데이터 | 필드·검증 |
|---|---|
| `onboarding` | 질문 ID별 `answerText`, `inputSource: typed/example/example_edited`, `confirmed`, `revision`. 자유 입력 원문은 본인 웹·서버만 보존. `answerPresetId`는 목표 v3의 필수 입력/추론 결과가 아님 |
| `profile` | `version`, `alias`, `avatarId`, `privateSummary`, `confirmed` |
| `privateSummary` | `interests`, `activityPreference`, `pace`, `conversationStyle`, `speakingStyle`, `expressionPresetIds`, `summarySource:user_confirmed_demo`. 지원 enum 중 본인이 별도 확인한 값만 사용. 미확인은 빈 배열/null, 자동 추정 없음 |
| `publicApproval` | `status`, `profileVersion`, `publicationVersion`, `approvedFields`, `introTemplateId`. 현재 본인 요약과 공개 항목의 정확한 조합 승인 |
| `publicProfile` | 승인된 필드만으로 서버가 파생. 클라이언트가 보낸 완성 소개·상대 공개용 임의 JSON을 그대로 사용하지 않음 |

`answerText`는 JSON 문자열이며 공백만인 입력을 거부하고 원문 기준 1~500 Unicode 코드 포인트로 검증한다. 빈 값 검사에만 trim을 쓰고 저장 원문·띄어쓰기·줄바꿈·이모지·ㅋㅋ/ㅎㅎ를 프리셋이나 정규화 문장으로 바꾸지 않는다. 예시 클릭은 로컬 초안 변경이고 별도 전송 성공 뒤에만 답변·revision을 저장한다. 오류·재시도는 같은 commandId·같은 본문을 유지하며 수정 전송은 새 명령으로 처리한다. 텍스트는 HTML로 해석하지 않는다.

준비된 후속 질문은 questionId/차례로 고른다. `demoCueId`가 필요하면 준비 대사 선택용 메타데이터로만 쓰고 원문의 의미 분석·프로필 근거로 사용하지 않는다. SUMMARY에는 원문과 시연용 소개값을 구분해 보여주며 PROFILE_CONFIRM의 `confirmedSummary`에 본인이 확인한 지원값만 전달한다. ‘소개값 사용 안 함’은 미확인 항목을 비우고 최소 소개/본인 여행으로 계속한다. 원문은 publicProfile·car projection·handoff·B 대사에 넣지 않으며 저장/초기화의 대상이다. 원문 수정은 기존 요약 확인·공개 승인·전달/ACK를 무효화하고 다시 확인하게 한다.

대표 관심사는 `sea_walk`·`cafe`, 활동 선호는 `walk_first_photos_occasional`, 속도는 `relaxed`, 대화는 `quiet`다. A 표현은 `calm`·`light_humor`를 지원하고 B는 승인된 고정 `gentle_polite`와 표현 ID를 사용한다. `expressionPresetIds`는 확인한 답변·소개 예시에서 선택한 표현만 가리킨다. 별명은 NFC 정규화·앞뒤 공백 제거 후 Unicode 코드 포인트 1~10개, 줄바꿈 불가로 웹·서버·차량에서 통일한다. 외형은 `a-01`·`a-02`만 허용한다. 표시할 때 별명을 HTML로 삽입하지 않고 텍스트로 처리한다.

프로필을 수정하면 버전을 올리고 공개 승인을 `pending`으로 바꾼다. `approvedFields`는 서버가 정한 공개 가능 항목의 부분집합이다. 원문 채팅·상세 일정·실명·전화번호·생년월일·차량번호·현재 좌표·숙소 주소는 공개 필드가 될 수 없다. 차분한 표현에서는 웃음 표현을 뺀 템플릿을 사용한다. 전체 공개 보류는 `private`이며 본인 여행은 계속 이용할 수 있다.

공개 승인은 필드 단위다. 다른 여행자와 연결할 공개 소개에는 별명·캐릭터 확인이 필요하고 관심사·활동 선호·성향·표현은 선택한다. 최소 소개 공개도 보류하면 private 모드를 사용한다. 선택하지 않은 필드는 추천 설명·상대 차의 대본에서도 제외한다.

공개 항목·승인 상태만 바뀌어도 publicationVersion을 올린다. 본인 요약 수정은 profileVersion을 올리고 공개 승인을 대기로 바꾼다. 표현 미공개 방문 캐릭터는 02번 INTRO_NEUTRAL을 사용하며 본인 private speakingStyle로 대체하지 않는다. 본인의 내 친구만 확인한 비공개 취향·표현을 사용할 수 있다.

서버는 소개·추천·방문 캐릭터 대사를 현재 확인·승인된 필드로 생성한다. 비공개/미확인 항목이 필요한 문장은 생략하거나 중립·일정 중심 대본으로 대체한다. 문장 일부만 지워 의미가 바뀌게 하지 않는다. 자유 답변이 대표 소개값과 달라도 원문을 보존하며 시연 프리셋으로 교체하거나 공통 취향을 임의로 만들지 않는다.

S06은 공개 프로필 기반 답변이며 메시지 요청을 만들지 않는다. S07은 별도의 `requestId`가 있는 사용자 메시지다. 메시지 대기 중 목록·다른 콘텐츠로 나가도 요청은 남는다. 답장이 오면 저장하되 화면 강제 전환·자동 낭독은 하지 않는다. 읽음 표시는 차량의 회차별 UI 기록으로 관리하며 메시지 전달 성공·상대 동의로 사용하지 않는다.

DM06의 목적은 서로 알아가고 스몰토크를 돕는 것이다. 현재 계약은 캐릭터 질문·답변과 확인한 말 전달을 구현하며, 밸런스 게임은 제작 채택 미정인 확장 예시다. 게임 상태·점수·응답 명령은 이번 계약에 추가하지 않는다. 채택할 때는 실제 사용자 응답과 공개 정보 기반 캐릭터 답변을 분리해 01~05의 대본·상태·검수를 함께 확정한다.

새 회차의 프로필은 기본 표시값만 있고 confirmed=false·공개 pending이다. 계획 미저장, 연결 none, messages는 빈 배열, 통화 idle, 만남 none, final·ending은 null, 차량 상태는 미확인으로 시작한다. `nav.cleanupRequired`는 자기 경유지가 남거나 정리 확인이 필요한 사실이고 `recovery.required`와 같지 않다. 정상 추가된 경유지의 존재만으로 만남·결말 재시연을 잠그지 않는다. 미확정 처리·예상 밖 경로에는 복구 잠금을 적용한다.

finalRound는 첫 만남 종료 전에는 0이다. 최초 유효한 MEETING_END에서 finalRound=1·새 finalId·final.status=pending·A/B 미선택·requestId=null을 같은 저장 단위로 만든다. 여기서 final.id는 명령의 finalId, final.round는 finalRound에 대응한다. 생성한 finalId·round와 현재 actionBindings를 차량 P04에 반환하며, 아직 B 응답은 열지 않는다.

추천·연결은 별명/캐릭터 소개와 여행 publicSummary가 모두 승인됐을 때만 연다. 선택 취향이 비공개여도 최소 공개가 유효하면 일정 중심 이유로 추천할 수 있다. 관심사 미공개를 지원 외 입력으로 오인해 프리셋·공개 상태를 바꾸지 않는다.

한 회차에는 연결 요청 한 건만 진행한다. CONNECT_REQUEST 접수 또는 해당 미확인 명령의 취소 확정으로 connection.attempted를 true로 두고 종료 후에도 유지한다. 거절·취소·종료 뒤 새 연결과 프로필/계획 재설정은 전체 초기화로 한다. 공개 철회는 연결 종료 뒤 PROFILE_PRIVATE로 가능하지만 새 연결 자격을 되살리지 않는다.

일반 통화와 MC 참여는 별도 동의다. MC 거절·취소는 일반 통화 동의를 지우지 않지만, 통화 종료는 해당 MC와 대기 요청을 함께 끝낸다. 연결 종료는 메시지·통화·MC 요청을 닫고 이후 응답을 무효화한다.

## 4. HTTP API 계약

### 4.1. 공통 규칙

JSON은 UTF-8이며 `/api` 응답은 `Cache-Control: no-store`를 사용한다. 요청 역할은 `X-Demo-Actor: web / car / operator`이고 POST의 `actor`와 일치해야 한다. 이것은 로컬 시연의 역할 구분이며 실제 서비스 인증·계정 접근 통제를 구현한 것으로 설명하지 않는다. 서버는 역할별 명령·현재 대상·상태를 다시 검증한다.

웹은 `X-Demo-Client-Id`에 webClientId를 보내고 서버는 최근 조회·명령 수신을 기록한다. 초기화 시 최근 5초 내 접속한 웹을 ACK 대상으로 고정한다. 접속 기록은 업무 동의가 아니며 version을 올리지 않는다. 닫힌 웹을 다시 열면 같은 ID로 초기화 상태를 읽어 UI 정리·ACK를 수행한다. 차량은 별도의 deviceId·vehicleSessionId를 사용한다.

| API | 입력 | 응답·효과 |
|---|---|---|
| `GET /health` | 없음 | schemaVersion·storeId·서버 시작 상태. 준비 안 됐으면 503 |
| `GET /api/scenario` | 역할 헤더 | 현재 역할에 허용한 프리셋·소재·공개 대사·capabilities. 원본 전체나 아직 발생하지 않은 B 메시지는 반환하지 않음 |
| `GET /api/state?view=web` | view는 web/car/operator, 역할과 일치 | 현재 projection·version·`allowedActions`·대기 대상. 조회는 사용자 행동을 실행하지 않음 |
| `GET /api/handoff` | car 역할 | 현재 유효한 전달 스냅샷. 미준비는 409. 읽기만으로 ACK 생성 없음 |
| `GET /api/commands/{commandId}?runId={runId}` | 원래 명령 역할 | `applied` 영수증 또는 `not_found`. not_found는 아직 도착하지 않은 요청까지 실패로 확정하는 뜻이 아님 |
| `POST /api/commands` | 아래 공통 봉투와 명령별 payload | 검증·원자적 저장 후 영수증·현재 역할의 최신 상태 |

`GET /api/state`는 본인·상대의 업무 상태와 화면에 필요한 데이터만 반환한다. 콘텐츠 목록은 `allowedActions`·연결·capabilities로 파생하고, 클라이언트의 화면 이름을 서버 권한 검증 근거로 사용하지 않는다.

`/api/scenario`의 대본·소재도 현재 공개 범위·연결 모드에 맞춰 필터링한다. my_trip 응답에 B 대화 대본을 기본으로 넣거나, 미발생 사용자 메시지를 미리 내려보내 UI에서만 감추지 않는다. 범용 버튼 문구·본인 대본과 조건이 충족된 상대 캐릭터 대본을 구분한다.

### 4.2. 요청·응답 예시

O01이 현재 만남 제안을 수락하는 요청이다. ID는 이미 서버가 발급한 대기 대상과 일치해야 한다.

```json
{
  "schemaVersion": 3,
  "runSeq": 1,
  "runId": "run-demo-01",
  "commandId": "cmd-demo-09",
  "expectedVersion": 12,
  "actor": "operator",
  "type": "B_RESPONSE",
  "target": {"kind": "meeting", "requestId": "req-meeting-01", "proposalId": "proposal-01"},
  "payload": {"decision": "accept"}
}
```

```json
{
  "ok": true,
  "receipt": {
    "runId": "run-demo-01",
    "commandId": "cmd-demo-09",
    "applied": true,
    "replayed": false,
    "committedVersion": 13
  },
  "state": {
    "schemaVersion": 3,
    "storeId": "store-demo-01",
    "runSeq": 1,
    "runId": "run-demo-01",
    "version": 13,
    "view": "operator",
    "meeting": {"proposalId": "proposal-01", "status": "confirmed"},
    "allowedActions": ["B_MEETING_CANCEL", "RESET_BEGIN", "SET_TEST_RESTRICTION"],
    "actionBindings": {
      "B_MEETING_CANCEL": {
        "commandType": "B_RESPONSE",
        "target": {"kind": "meeting", "requestId": "req-meeting-01", "proposalId": "proposal-01"},
        "payload": {"decision": "cancel"}
      }
    }
  }
}
```

`state` 예시는 주요 필드만 보인다. 전체 projection은 3절의 범위를 따른다. O01 응답에 차량의 내비 승인 동작을 넣지 않는다. `allowedActions`는 버튼용 의미 ID다. 예를 들어 `B_MEETING_CANCEL`은 아래 `B_RESPONSE`의 만남 취소로 직렬화되며, SDK 실행을 허가하는 별도 역할이 아니다.

의미 ID와 RPC 명령이 다르면 `actionBindings[id]`에 commandType·현재 target·고정 payload를 반드시 제공한다. 위 JSON은 해당 바인딩 한 건만 보인다. UI는 현재 runId/version·새 commandId·허용된 사용자 입력을 합쳐 전송하고 바인딩을 장기 캐시하지 않는다. 비활성 사유는 `blockedActions[id]`의 code/message로 제공한다. 바인딩도 권한 토큰은 아니며 서버는 실제 상태·역할·대상을 다시 검사한다.

```json
{
  "ok": false,
  "error": {"code": "STALE_STATE", "message": "새 정보가 있어요. 다시 확인해 주세요."},
  "state": {"storeId": "store-demo-01", "runSeq": 1, "runId": "run-demo-01", "version": 14, "view": "car"}
}
```

| HTTP·코드 | 의미·클라이언트 처리 |
|---|---|
| 400 `INVALID_PAYLOAD / COMMAND_ID_REUSED` | 형식·enum·ID 본문 재사용 오류. 수정 없이 재시도하지 않음 |
| 403 `ACTOR_FORBIDDEN` | 역할에 허용되지 않은 조회·명령 |
| 404 `NOT_FOUND` | 존재하지 않는 API·대상. 명령 조회는 200과 not_found 상태로 응답하며 미도착 요청의 실패 확정이 아님 |
| 409 `STALE_STATE / RUN_CHANGED / NOT_READY / INVALID_TRANSITION / COMMAND_CANCELLED` | 최신 상태를 다시 읽고 사용자에게 현재 선택을 확인. 취소 표식이 있는 원래 명령은 실행하지 않음. 자동 재실행 없음 |
| 423 `RESTRICTED / RESETTING / RECOVERY_REQUIRED` | 차량 제한·초기화·외부 경로 미정리. 원인 해소 전 잠금 |
| 500 `STORE_FAILED` | 상태 저장 실패. 성공 표시 금지·복구 후 같은 명령 결과부터 확인 |
| 503 `UNAVAILABLE` | 서버·필수 데이터가 준비 안 됨. 조회 재연결·준비 상태 안내 |

### 4.3. 명령 영수증·동시성

서버는 **중복 영수증 확인 → 회차·역할·버전·대상·제한 검증 → 새 상태 계산 → 영수증과 상태 저장 → 성공 응답**을 하나의 순차 작업으로 처리한다. SDK 결과를 기다리며 큐를 점유하지 않는다.

- 중복 키는 `(runId, actor, commandId)`다. 같은 키·같은 본문이면 재적용하지 않고 기존 영수증과 현재 projection을 반환한다. 같은 키로 본문·예상 버전을 바꾸면 400이다.
- 원래 명령이 성공했다면 이후 version이 올라가도 같은 전송의 중복 확인은 성공 영수증을 반환할 수 있다. UI는 영수증의 회차와 현재 상태를 대조하고 이전 성공으로 새 결말·동의를 표시하지 않는다.
- 새 사용자·O01 업무 명령은 `expectedVersion`이 다르면 409다. 최신 버전을 읽었다고 사용자 선택을 자동 재실행하지 않는다. 새 확인 행동은 새 commandId다.
- 상태·영수증·내비 작업 기록을 같은 저장 단위로 유지한다. 임시 파일 작성·동기화 후 같은 디렉토리에서 교체하고, 저장 성공 전 메모리 상태를 확정·응답하지 않는다. 교체 전 실패는 새 상태를 반영하지 않는다. 교체 직후 저장 결과가 불확실하면 일반 쓰기를 중단하고 파일·영수증을 재검증한다. 이전 메모리 상태로 새 파일을 덮어쓰거나 미적용으로 단정하지 않는다.
- HTTP 시간 초과 시 먼저 명령 영수증과 현재 상태를 조회한다. 적용됐다면 결과만 반영하고, 미확인이면 확인 중으로 유지한다. 사용자가 같은 전송을 다시 시도할 때에만 동일 ID·본문을 사용한다.
- 미확인 요청을 버리고 새 ID로 전송하지 않는다. 취소가 필요한 요청은 해당 requestId를 무효화하는 취소 명령을 사용한다. SDK 시도는 8절의 별도 정리 규칙을 따른다.
- `CAR_STATUS`·`NAV_REPORT`·`RESET_ACK` 같은 사실 보고는 이전 업무 version에서도 받을 수 있다. 대신 현재 차량 세션·증가 번호·알려진 attempt·resetId를 검증한다. 이것으로 새 동의·장면 진행을 만들지 않는다.

요청 생성 응답이 유실되어 requestId를 아직 모를 때의 취소는 `CANCEL_PENDING_COMMAND`를 사용한다. 서버는 원래 commandId가 아직 미적용이면 취소 표식을 먼저 저장해 늦은 원래 요청을 막는다. 이미 적용됐으면 영수증이 가리키는 요청에 해당 취소·종료를 적용한다. 이미 전달된 메시지를 회수됐다고 표시하거나 이미 실행된 SDK 효과를 없던 일로 만들지 않는다.

상태 파일이 읽히지 않거나 schema가 맞지 않으면 기본 상태로 덮어쓰지 않고 준비 실패로 시작한다. 단일 서버 프로세스만 같은 runtime 파일을 쓴다. 운영 DB의 동시 접속·확장성을 보장하는 구조로 설명하지 않는다.

## 5. 명령·역할·필수 조건

아래는 POST의 `type`과 필수 payload·대상이다. 공통 봉투는 4절을 따른다. `allowedActions`는 같은 검증 함수로 계산한다. 목록에 버튼이 있더라도 실행 시 다시 검증한다.

### 5.1. 준비·연결·이어받기

| 명령 | 역할 | 대상·payload·조건 |
|---|---|---|
| `ONBOARDING_ANSWER` | web | v3: questionId·answerText·inputSource. 연결 시도 전 현재/기존 질문 자유 입력·수정. 예시 선택만으로 호출하지 않음. 원문 수정 시 요약·공개 승인·전달 재확인, 외부 전송 없음 |
| `PROFILE_CONFIRM` | web | v3: alias·avatarId·confirmedSummary. 질문 원문 확인과 별도 소개값 확인 뒤 저장. 미확인 항목은 비움. answerText 자동 enum 매핑 금지 |
| `PROFILE_UPDATE` | web | 수정할 지원 필드. connection.attempted=false 준비 상태만, 버전 증가·공개 승인 대기·전달 무효화 |
| `PROFILE_PUBLISH` | web | 현재 profileVersion·approvedFields·introTemplateId. 정확한 소개 버전 확인 뒤 공개 snapshot 파생 |
| `PROFILE_PRIVATE` | web | 현재 profileVersion·publicationVersion. 공개 보류·철회·본인 여행 모드. 유효한 상대 요청은 먼저 종료, attempted는 유지 |
| `TRIP_SAVE` | web | presetId·shareSummaryApproved. 연결 시도 전 본인 확인 후 저장. 소개와 여행 요약 공개가 모두 유효해야 추천 ready |
| `CONNECT_REQUEST` | web | peerId=B·현재 프로필/공개/계획 버전. 추천 가능·attempted=false일 때 connectionId·requestId 발급·attempted=true |
| `CONNECT_CANCEL` | web | 현재 connectionId·requestId. 요청 또는 시간 확인 대기 취소. 늦은 수락 무효화 |
| `CONFIRM_WINDOW` | web | connectionId·수락된 requestId·고정 공통 시간 ID. B 수락 후에만 linked |
| `CONNECT_END` | web/car | connectionId·종료 맥락. 연결·메시지·통화·MC 종료. 시작 전 약속은 취소·정리 파생. ended 만남·checkpoint와 terminal final은 보존, normal의 pending final은 5.2.1절대로 B 대기 정리 |
| `HANDOFF_PREPARE` | web | mode=`connected` 또는 `my_trip`. 유효한 본인 프로필·계획 필요. connected는 최신 linked·공개 승인도 필요 |
| `CAR_SESSION_OPEN` | car | deviceId·새 실행 세션 ID·로컬 미정리 attempt 목록. 같은 장치 재접속은 복구 중에도 허용하며 새 vehicleEpoch 발급. 새 SDK 실행 허가는 아님 |
| `CAR_LOADED` | car | handoffId·handoffVersion·참조 버전·mode·vehicleSessionId. 최신 전달본을 검증한 ACK일 때만 차량 확인 완료 |
| `CAR_STATUS` | car | 세션·statusSeq·제한 확인/적용·foreground·UI 맥락. 사실 보고, 단순 heartbeat는 업무 version 증가 없음 |
| `CANCEL_PENDING_COMMAND` | web/car | 같은 역할·회차의 originalCommandId·originalType. 생성 응답 미확인인 연결·메시지·통화·MC·만남·내비 승인에 한해 적용 |

추천은 `TRIP_SAVE` 또는 이후 유효한 공개 승인 처리의 결과로 준비한다. 별도의 필수 ‘매칭 찾기’ 명령은 없다. 조회·UI 표시 오류는 실패로 안내하고 실제 후보 부족으로 표현하지 않는다.

ONBOARDING_ANSWER·PROFILE_CONFIRM·PROFILE_UPDATE·PROFILE_PUBLISH·TRIP_SAVE는 connection.attempted=false일 때만 허용한다. 연결 종료 뒤 공개 철회인 PROFILE_PRIVATE는 예외지만 새 후보·연결을 열지는 않는다. attempted=true인 회차는 기존 준비 화면을 열어도 수정·새 요청으로 우회하지 못한다.

취소 대상 생성 명령은 `CONNECT_REQUEST`, `MESSAGE_SEND`, `CALL_PROPOSE`, `MC_PROPOSE`, `MEETING_PROPOSE`, `NAV_APPROVE`다. 원래 명령이 이미 적용됐다면 해당 연결 종료·통화 종료·MC 제외·만남 취소로 처리하되 현재 대상과 취소 가능 구간을 확인한다. MESSAGE_SEND가 적용됐다면 already_sent와 현재 대화를 반환하고 메시지 회수로 표현하지 않는다. NAV_APPROVE는 만남 취소와 실제 정리 필요 상태를 유지한다. 이후 requestId를 알게 되면 일반 취소 명령을 사용한다.

| `MEETING_DECLINE` | car | connectionId. 제안 전 이번 만남을 진행하지 않기. 상대 연결 종료·early_end |
| `MEETING_CANCEL` | car | connectionId·proposalId 또는 현재 제안 requestId. 제안~만남 시작 전. 내비 요청 중·후에도 가능 |
| `FINAL_CHOOSE` | car | 현재 finalId·finalRound·choice=`together / my_agent`. pending에서 my_agent는 즉시 각자 결과·B 요청 무효화. normal의 together는 linked 필요, final_replay는 유효 checkpoint 필요 |
| `REVIEW_APPLY / REVIEW_SKIP` | car | 현재 finalRound·장식 ID. 함께 결말·추가 후기 화면·capabilities 활성일 때만 |
| `SAVE_REASON` | car | 현재 finalRound·이유 프리셋. 선택 기능 활성 + A가 직접 my_agent 선택한 경우만. 상대 projection에서 제외 |

온보딩 타이핑·예시 칩으로 초안 채우기·수정, 차량의 질문/답변 칩 선택, 콘텐츠 목록 이동, 휴식, 내 일정 보기, 음성 중단·다시 듣기는 로컬 UI 동작이다. 이것으로 서버 요청·동의를 생성하지 않는다. S06 대본은 현재 B 공개 프로필에 허용된 문장만 보여주며 근거가 없으면 모름 안내와 S07 문장 확인으로 이동한다.

MC 콘텐츠로 처음 들어가도 일반 통화의 양쪽 동의를 먼저 확인하고, MC 초대에 다시 동의받는다. 만남 버튼은 특정 대화 완료 여부를 요구하지 않는다. 활성 통화·MC 제안은 먼저 종료·취소해야 만남으로 갈 수 있다. 메시지 답장 대기는 만남 제안을 강제로 막지 않지만, 연결 종료 시에는 함께 종료한다.

일반 통화의 active는 동의한 샘플 세션이다. 로컬 재생 상태 ready/playing/paused/finished와 구분하고 포커스 상실·앱 복귀로 새 동의를 만들거나 자동 재생하지 않는다. 명시적 CALL_END 전에는 만남 제안을 잠근다. 메시지 전송 성공은 시연 서버 수신·저장 확인이며 실제 상대 열람·실시간 통신의 증빙이 아니다.

FINAL_CHOOSE와 최종 B_RESPONSE는 같은 round에서 서버 저장 순서로 확정한다. 결과가 함께/각자로 확정되면 terminal이며 이후 도착한 변경은 INVALID_TRANSITION 또는 STALE_STATE다. 아직 pending일 때만 A의 각자 변경을 허용한다. 확정 결과 변경은 새 finalRound를 만드는 REPLAY_FINAL로만 한다.

### 5.2.1. 최초 최종 선택과 B 요청의 발급

| 전이 | final·요청 처리 | 화면·허용 동작 |
|---|---|---|
| 첫 MEETING_END | meeting=ended·checkpoint와 함께 finalRound=1·새 finalId·pending·A/B=null·requestId=null 생성 | P04.CHOICE. A 선택만 열고 O01 B 버튼은 잠금 |
| A가 처음 together | A=together·새 최종 requestId·B=null을 원자적으로 저장 | P04.PEER_WAITING. 이 requestId에 대한 B 최종 응답만 허용 |
| A가 처음 my_agent | 즉시 final.status=my_agent·B=null·requestId=null | B 대기 없이 내 친구 결말. 완료된 만남·checkpoint는 보존 |
| B 대기 중 A가 my_agent | 해당 B 요청을 종료·활성 requestId=null, 종료된 ID는 영수증·요청 이력에 보존 | 내 친구 결말. 늦은 B 응답 거부 |
| 현재 요청의 B가 together/my_agent | A=together·pending·동일 requestId/round와 normal의 linked 또는 replay의 유효 checkpoint를 확인. 결과 확정·활성 requestId=null | 함께 또는 내 친구 결말. 확정 응답의 ID는 이력으로 보존 |
| normal에서 pending 중 CONNECT_END | 활성 B 요청 종료·requestId=null. 현재 A/B 선택은 null로 되돌리고 이전 선택·요청 이력, finalId/round·pending·완료 만남·checkpoint는 보존 | P04.CHOICE로 돌아가 함께는 잠금. A가 내 친구와 이어가기를 직접 선택하면 각자 결과 확정 |

같은 명령 재전송은 기존 영수증을 반환하며 finalId·requestId·round를 다시 만들지 않는다. 이미 B 대기 중인 together 선택으로 새 요청을 중복 생성하지 않는다. MEETING_END를 새 명령 ID로 다시 보내도 이미 ended라면 새 round를 만들 수 없다. 재시연은 9.2절에서 새 finalId·round를 만들고 같은 A 선택→필요한 B 요청 순서를 따른다.

위 연결 종료 처리는 normal에 적용하며 종료된 연결의 B 응답을 계속 기다리거나 A의 각자 선택을 자동으로 만들어내지 않는다. 이미 확정된 final은 연결 종료로 바꾸지 않는다. final_replay에서는 live 연결 종료와 표시용 최종 선택을 분리하고 9.2절의 checkpoint 조건을 따른다.

`B_RESPONSE.kind`는 `connection / message / call / mc / meeting / final`이다. connection·call·mc·meeting은 accept/reject, message는 reply, final은 together/my_agent를 받는다. 만남 수락 후 취소는 같은 kind에 cancel과 proposalId를 보낸다. 최종 응답에는 finalRound도 필수다. 본문 자유 B 답변은 받지 않고 요청에 대응하는 fixture 문장을 사용한다.

종류·requestId와 관련 connectionId/threadId/callId/proposalId/finalId/finalRound는 target, decision은 payload에 둔다. 해당 요청에서 필요하지 않은 ID는 생략하고 서버가 발급한 바인딩을 사용한다. NAV_REMOVE_APPROVE의 reset_cleanup은 만남 cancelled 상태를 요구하지 않는다. 같은 resetId의 자기 경유지 정리임을 확인하고 add·장면 진행 잠금은 유지한다.

차량용 B 대화·동의 응답, 만남 시간 전환, 최종 재시연은 차량 잠금 중 허용하지 않는다. 웹 준비·S04 연결용 B 응답은 차량 미접속이어도 가능하다. 이미 알려진 취소·SDK 결과·정리 사실은 잠금 중에도 기록한다.

## 6. 모바일·차량 이어받기와 화면 동기화

### 6.1. 전달 스냅샷

`HANDOFF_PREPARE`는 현재 상태에서 전달본을 만들고 참조 버전을 묶는다. 이후 본인 요약·공개·계획·연결 버전이 바뀌면 이전 전달본을 무효화한다. 같은 참조 버전·mode의 준비 요청은 기존 ID/버전을 재사용한다. 단순 메시지·heartbeat 변경으로 전달본을 무효화하지 않는다. 아래는 본인 여행 모드 예시다. connected 모드에만 B 공개 프로필·connectionId·공통 시간이 추가된다.

```json
{
  "schemaVersion": 3,
  "runSeq": 1,
  "runId": "run-demo-01",
  "handoffId": "handoff-01",
  "handoffVersion": 3,
  "sourceVersions": {"profile": 2, "publication": 1, "trip": 1, "connection": 0},
  "mode": "my_trip",
  "owner": {
    "alias": "파도",
    "avatarId": "a-02",
    "summary": {"interests": ["sea_walk", "cafe"], "activityPreference": "walk_first_photos_occasional", "pace": "relaxed", "conversationStyle": "quiet", "expressionPresetIds": ["a-sea-coffee"]},
    "speakingStyle": "light_humor"
  },
  "ownerTrip": {
    "date": "2026-11-14",
    "nextVisit": "15:20", "nextVisitLabel": "기존 개인 방문지",
    "returnPlaceId": "a-lodging-01", "returnPlaceLabel": "내 숙소",
    "returnEstimate": "15:45", "returnDeadline": "16:00"
  },
  "peer": null
}
```

1. 웹은 전달 준비 저장 성공 뒤 ‘차량에서 불러오세요’를 표시한다.
2. 차량 P01은 사용자가 누를 때 현재 회차·schema·handoffVersion·참조 버전·mode·실제 제한을 확인한다.
3. connected는 최신 linked·공개 프로필·공통 시간, my_trip은 본인 정보만 검증한다. 기본 B 샘플로 연결을 대신하지 않는다.
4. 차량이 검증한 동일 handoff ID·버전으로 `CAR_LOADED`를 보낸다. 그 사이 변경됐으면 409로 다시 불러오게 한다.
5. 서버가 ACK를 저장한 뒤에만 웹 M04에 ‘차량에서 이어졌어요’를 표시한다. 단순 GET·불러오기 애니메이션은 성공 ACK가 아니다.

CAR_LOADED는 읽은 전달본 확인만 갱신한다. 같은 장치의 중복 ACK나 새 세션 ACK로 메시지·통화·만남·최종 결과를 초기화하지 않는다. 재불러오기 후 초기화/복구 확인, 만남 종료 후 최종 선택·결과 P04, 만남/내비 P03, linked P02, 본인 모드 순으로 현재 상태를 복원한다. 첫 소개는 해당 연결에서 아직 제공하지 않은 경우에만 사용한다.

공개를 보류했거나 연결을 끝냈어도 유효한 본인 요약·계획을 my_trip으로 전달할 수 있다. 이 경우 상대 콘텐츠·만남 권한은 없다. A의 공개 소개를 B 차에 보여주는 장면은 승인된 publicProfile projection의 미리보기이며 실제 B 차량 접속 구현은 필수가 아니다.

### 6.2. 조회·재진입·허용 동작

클라이언트는 같은 storeId에서 `(runSeq, version)`이 더 오래된 응답으로 화면을 덮어쓰지 않는다. 회차가 바뀌면 미전송 초안·새 답장 표시·음성·로컬 재생 위치·대기 요청 UI를 지우고 새 상태를 읽는다. storeId가 달라지면 자동으로 새 실제 연동을 시작하지 않고 기록 대조·복구를 요구한다.

이미 현재 run의 전달을 ACK한 같은 deviceId는 재접속 후 최신 state로 진행 상황을 복원할 수 있다. 이후 연결·공개 상태 변화가 과거 ACK 증빙 자체를 삭제하거나 매번 P01 첫 진입을 요구하지 않는다. 새 ACK에는 최신 snapshot을 요구하고, 본인 프로필·계획이 바뀐 준비 단계에서는 새 전달본을 명시적으로 확인한다. ACK는 상태 표시의 근거이지 연결·동의의 현재값을 고정하는 권한이 아니다.

| 화면 | 서버 상태·로컬 UI 연결 |
|---|---|
| M01 | 질문·확인·공개 버전은 서버. 아직 고르지 않은 답변·펼침·별명 편집은 로컬 |
| M02·M03 | 계획·추천 결과는 서버. 카드 펼침·요약 보기·스크롤은 로컬 |
| M04·P01 | 연결·전달·ACK는 서버. 이전 snapshot으로 성공을 복원하지 않음 |
| P02 | 연결·메시지·통화·MC는 서버, 콘텐츠 선택·질문 열기·자막 위치는 로컬. 미발생 B 메시지 생성 금지 |
| P03 | 제안·동의·내비 attempt·취소·정리 상태는 서버와 실제 차량 기록 대조. UI 재생성에서 SDK 호출 금지 |
| P04·P05 | 최종 round·선택·결과·장식은 서버. 대화 펼침·일정 보기는 로컬이며 새 동의 없음 |
| O01 | 현재 UI 맥락은 차량 보고로 참고. 실행 가능 여부는 실제 업무 요청·대상·제한으로 계산 |

화면 변경 자체를 전역 stage 전환으로 저장하지 않는다. 여러 콘텐츠의 요청이 공존할 수 있으므로 sceneId는 발표·소재 연결용 참고값이다. 예를 들어 P02 목록에서도 유효한 메시지 요청은 남고, B 답변은 새 답장 표시만 바꾼다.

페이지 새로고침·앱 복귀에서는 먼저 최신 상태·제한·실제 내비 기록을 확인한다. 사용자 명령·통화 샘플·SDK 실행을 자동 재개하지 않는다. 전송 중이던 사용자 명령은 기존 commandId의 영수증부터 확인한다. 실패한 조회와 사실 보고의 재전송은 새 사용자 동의와 구분한다.

## 7. 차량 제한·수명주기·음성

### 7.1. 차량 상태와 서버 잠금

차량은 시작 시 `CAR_SESSION_OPEN`으로 세션을 등록하고 실제 제한의 현재값과 변경을 보고한다. 한 시연에서는 한 실행 차량만 바인딩한다. 다른 차량·세션으로 교체하려면 기존 작업·외부 경로 기록을 확인해야 하며 미확정 attempt를 새 차량이 자동 실행하지 않는다.

같은 deviceId의 앱 재시작은 초기화·복구 중에도 재접속을 허용한다. 서버가 새 vehicleEpoch를 발급하고 실제 제한은 미확인에서 다시 읽는다. reset의 차량 참여자는 deviceId로 묶으며 새로 등록된 현재 세션이 같은 장치의 기록을 대조해 ACK할 수 있다. 이전 세션 ACK는 거부한다. 다른 deviceId가 미정리 작업을 인수하거나 지우는 것은 허용하지 않는다.

NAV_REPORT는 attempt의 원래 executorSessionId와 현재 reporterSessionId를 구분한다. 같은 deviceId의 알려진 시도만 보고하며 현재 epoch의 route_snapshot을 최신 관측에 사용한다. 이전 epoch의 늦은 event는 journal에 남기고 재관측 필요를 표시할 수 있지만, 현재 경로·정리 완료를 과거 값으로 덮지 않는다. 같은 epoch 안에서는 observationSeq가 이전인 관측을 제외한다.

업무 조작의 기본 차량 잠금 식은 **실제 제한 OR 제한 미확인 OR 앱 비활성 OR 보고 만료 OR 시연용 제한**이다. 이는 새 전송·동의·내비 실행의 잠금 식이다. 주행 음성까지 이 Boolean 하나로 일괄 판정하지 않고 7.3절의 검증된 별도 capability를 사용한다. 미검증인 현재 v2는 기존 차단을 유지한다. 초기화·복구 잠금은 이 위에 명령 종류별로 적용한다. 차량은 서버 허용 목록이 있어도 로컬 실제 제한·비활성·네트워크 미확인 상태이면 실행하지 않는다.

| 명령 종류 | 초기화·복구 상태에서의 조건 |
|---|---|
| 새 연결·메시지·통화·만남·최종 진행 | 초기화 중 차단. 실제 미확정 처리의 복구 중에는 차량의 새 사회적 요청·시간 전환을 차단 |
| 새 실제 경유지 추가·새 실제 회차 | 실제 미확정 처리·기록 불일치·이전 외부 정리가 남으면 차단 |
| 경유지 제거 승인·remove 실행권 | 기본 차량 잠금이 없고 자기 작업·정리 대상이 확인되면 초기화·복구 중에도 허용. 정리해야 잠금이 풀리는데 정리 명령도 막히는 순환을 만들지 않음 |
| 연결·만남 취소·통화 중단·사실 보고 | 종료·중단·기록은 처리. 알려진 모의 시도의 NAV_MOCK_RESULT도 기록 가능하나 공통 version/대상 검사는 유지. 새 실제 경로 변경·동의를 만들지 않음 |
| 내 친구·본인 일정 조회 | 현재 상태와 정리 필요 안내를 유지해 표시 가능. 초기화 확인 화면을 우회해 새 회차를 시작하지 않음 |

`statusSeq`가 이전 번호이거나 vehicleSessionId가 바뀐 이전 보고는 무시한다. 수신 후 유효기간은 서버의 단조 증가 시간으로 계산한다. 같은 잠금 상태의 heartbeat는 version을 올리지 않지만, 잠금 적용·해제·만료는 업무 version을 올린다. 조회·명령 처리 직전에도 만료를 다시 계산해 오래된 allowedActions로 실행되지 않게 한다.

제한 중 화면의 새 질문 선택·전송·통화 시작·MC 초대·만남 동의·내비 승인·최종 선택·차량용 B 응답·시간 전환은 막는다. 검증된 driving_voice의 상대 캐릭터 음성 문답·쉬기·종료만 별도 조건으로 제공한다. 이 예외가 B 응답이나 사회적 동의를 발급하지 않는다. 이미 발생한 취소·SDK 결과와 플랫폼이 허용하는 음성·통화 중단은 계속 처리한다. 사실 보고가 사용자 선택을 대신하지 않게 한다.

공식 `CarUxRestrictionsManager`의 현재값·리스너를 사용하며 가상 기어 그림·속도로 추정하지 않는다. Android car 라이브러리 설정과 실제 API 접근은 작은 차량 프로젝트에서 먼저 빌드·검증한다. [Pleos 주행 규제 개발 가이드](https://document.pleos.ai/docs/pleos-only/vehicle-app-developer-guide/driving-restriction-development-guide)

### 7.2. 앱과 음성 수명주기

`DemoRepository`가 조회·명령·회차·영수증을 담당하고 `DemoViewModel`은 상태를 표시한다. 실제 SDK 실행은 화면 렌더링이나 Compose 재구성에서 호출하지 않는다. UI 작업은 메인 스레드, HTTP·저장은 IO 작업으로 분리한다.

`RestrictionMonitor`는 상태 미확인에서 시작하고, 앱 일시중지 시 foreground=false를 보고한다. 보고가 실패해도 로컬 UI·음성을 즉시 멈추며 서버는 보고 만료로 잠근다. 복귀 뒤 새 제한값·세션·현재 상태가 확인될 때까지 조작을 열지 않는다.

`VoicePlayer`는 한 번에 하나의 문장과 발화자만 재생한다. 준비된 MP3·자막은 같은 manifest ID를 사용하며, 실제 통화가 아닌 샘플을 통화 오디오 권한으로 가장하지 않는다. 초기 구현은 미디어 음성 샘플의 `USAGE_MEDIA`·`CONTENT_TYPE_SPEECH`와 적절한 오디오 포커스 요청을 사용하고 실제 Pleos 정책에서 확인한다.

포커스 거절·상실·일시 상실·앱 숨김·blocked 진입은 녹음/재생을 중단하고 duck 이벤트는 정책에 따라 감쇄/일시중단한다. 주행 상태 전환 자체는 검증된 driving_voice의 허용 범위와 대조하며 음성을 무조건 중단하는 기준으로 쓰지 않는다. 포커스가 돌아왔다고 대사·다음 행동을 자동 실행하지 않는다. 사용자가 정차 상태에서 현재 문장 다시 듣기를 선택할 수 있다. 무음·음성 누락에도 자막과 같은 동의 조건으로 진행한다. [Pleos 오디오 포커스 가이드](https://document.pleos.ai/docs/pleos-only/vehicle-app-developer-guide/audio-focus-development-guide/audio-focus-development)

실제 주행 중 지원은 01~03번의 별도 검증 범위다. TTS·STT·FusedLocation·실시간 통화·생성형 AI는 기본 의존성에 추가하지 않는다. 이를 나중에 연동할 때는 권한·지원 상태·공개 범위·새 검수 항목을 함께 갱신한다.

### 7.3. 주행 중 음성 모드의 목표 계약 · v3, 미구현

| 필드·상태 | 계약 |
|---|---|
| `interactionMode` | `parked / driving_voice / blocked`. 앱이 임의로 주행 허용을 선언하는 값이 아니라 검증 조건으로 계산한 결과 |
| 제한 관측 | requiresDistractionOptimization·activeRestrictions·현재 세션·statusSeq·foreground·신선도. 플래그 하나로 전체 음성 금지를 추정하지 않음 |
| `voiceCapability` | `unverified / verified / unavailable`, 검증 환경·지역·차종/버전·DO/카테고리 심사 범위·evidenceId·검증한 기능. 현재값은 unverified |
| `voiceSession` | 같은 회차·상대 공개 버전·발화자에 묶고 `source:scripted/live`, `state:idle/speaking/listening/paused/ended`를 구분. scripted는 listening으로 표시하지 않음 |
| 시작 조건 | 기능별 정책 허용·DO/카테고리 증빙·현재 실제 제한·세션/신선도·foreground·마이크 권한·오디오 포커스 확인. 하나라도 미확인이면 blocked |
| 허용 | 공개 정보에 근거한 상대 캐릭터 음성 문답, 쉬기·종료. 원문 녹음의 외부 전송·장기 저장은 별도 승인/정책 없이 추가하지 않음 |
| 계속 잠금 | 목록·키보드·새 메시지/통화/MC·만남 동의·내비 승인·최종 선택·B 응답·이야기 시간 전환 |
| 중단·복귀 | 내비·안전 안내와 포커스 정책을 우선. 무응답 재촉 금지. 포커스/앱 복귀만으로 마이크·재생·업무 명령 자동 재실행 금지 |

`voiceCapability`는 클라이언트의 임의 true나 operator 이벤트로 실제 지원 증빙을 대신하지 않는다. v3 전환 시 서버·차량이 같은 검증 환경 allowlist와 지원 필드를 사용하고 불일치하면 blocked다. 초기화/복구 잠금은 음성에도 적용해 새 문답을 중단한다. 현재 v2 서버의 parked 전용 allowedActions를 완화하거나 existing restricted=false를 조작하지 않는다. 주행 음성 문답은 새 업무 RPC를 자동 생성하지 않는다.

정적 작은 캐릭터·발화자·한 줄 상태도 표시가 허용된 범위만 사용한다. 긴 자막으로 진행하거나 화면을 보지 않으면 답을 못 하게 만들지 않는다. 마이크/네트워크/인식 실패는 음성으로 짧게 알린 뒤 중단하고, 주행 중 터치 선택으로 전환시키지 않는다. 현재 목업은 준비된 대사를 주차/발표에서 재현한다.

쉬기·종료에서는 앱의 마이크 수집을 중단한다. 주행 중 재개는 지원을 확인한 시스템 음성 입력 경로 등으로 사용자가 명시한 경우만 검토하며, 앱 자체가 항상 듣고 있거나 임의 호출어를 지원한다고 가정하지 않는다. 재개 경로가 미검증이면 주차 후 재개한다. 이 부분도 V05의 마이크·수명주기 검증에 포함한다.

공식 [UI 가이드](https://document.pleos.ai/docs/connect/guide/docs-design/Introduction/intro)는 핸즈프리 음성 인터랙션을 다루고, [주행 규제](https://document.pleos.ai/docs/pleos-only/vehicle-app-developer-guide/driving-restriction-development-guide)는 기능별 실제 제한 반영을 요구한다. [SDK 신청 안내](https://document.pleos.ai/docs/pleos-only/create-my-project)의 STT/TTS 준비 중 상태와 API 문서 존재를 구분한다. Gleo function 호출 연동은 캐릭터 목소리/자유 대화의 자동 지원이 아니다. V05의 실제 심사·마이크·권한·오디오 포커스·제한 전환 검증은 미실시다.

## 8. NaviHelper 실제·모의 처리

이 절의 ‘내비 추가 요청’은 만남 장소를 **중간 경유지로 추가하는 작업**이다. 기존 목적지 D는 유지하고 만남 경유지 M만 추가·제거한다. 이야기에서 D는 기존 다음 방문지, M은 만남 카페 역할이며, 아래 실제 SDK 시험은 그 역할만 대응시킨 별도 좌표를 쓴다. 일정의 숙소 복귀 장소는 D와 별개이고 이 기능이 숙소를 목적지로 자동 설정하지 않는다.

사용자가 보는 순서는 ‘현재 위치 → D’에서 ‘현재 위치 → M → D’로 변경하는 것이다. M 제거 뒤에는 현재 위치에서 D로 가는 안내를 확인하며, 과거 경로·ETA의 동일한 복원이나 숙소 도착을 보장하는 것으로 표시하지 않는다.

### 8.1. Adapter와 SDK 확인 범위

앱의 Adapter는 `initialize`, `observeRoute`, `addApprovedWaypoint`, `removeApprovedWaypoint`, `release` 책임으로 나눈다. 이 이름은 앱 내부 계약이며 SDK의 실제 메서드 이름이 아니다. `MockNaviAdapter`와 `RealNaviAdapter`가 결과 출처를 항상 붙여 반환한다.

| 기능 | 공식 SDK에서 확인한 API·조건 |
|---|---|
| 초기화·해제 | `NaviHelper` 생성, `initialize(onConnected, onFailed)`, 동일 리스너 등록·제거, `release()` |
| 목적지 확인 | `getDestinationInfo()`. 즉시 반환값이 아니라 이벤트로 결과 수신 |
| 경유지 확인 | `getWaypointInfo()`와 경유지 정보 콜백 |
| 추가·제거 | `addWaypoint(RequestWaypointInfo)`·`removeWaypoint(WaypointIndex.FIRST)` |
| 이벤트 | `onRoutingCompleted`, 목적지·경유지 변경, 정보 조회·오류. 현재 Navigation 구현에 따라 전달이 달라질 수 있음 |
| 권한 | 조회 `pleos.car.permission.NAVI_ROUTE`, 추가·제거 `pleos.car.permission.NAVI_ROUTE_SEARCH`, Navigation 화면 요청을 사용할 때만 `pleos.car.permission.NAVI_CUSTOM_MAP` |

[SDK 초기화·해제](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/NaviHelper/initialization-and-release), [목적지 조회](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/NaviHelper/destinations), [경유지 추가·조회·제거](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/NaviHelper/waypoint-settings), [이벤트](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/NaviHelper/event-listeners), [권한](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/NaviHelper/declaring-permissions)

의존성 동기화 후 배포 SDK의 실제 인터페이스로 콜백 철자·인자·권한을 확인한다. 문서 예제의 경유지 콜백 표기가 다른 부분을 임의의 시그니처로 복사하지 않는다. SDK 초기화 성공 전에 호출하지 않고 리스너를 중복 등록하지 않는다. 실제 Navigation 화면은 플랫폼이 제공하며 앱의 모의 경로 그림과 구분한다.

### 8.2. 별도 시험 경로

대표 이야기의 강릉 카페는 가상 장소이고 SDK 시험 좌표가 아니다. 실제 연동은 개발자가 소유한 에뮬레이터 시험 경로에서만 검증한다.

| 구분 | SDK 시험값 |
|---|---|
| D 원래 목적지 | latitude 37.48544722 · longitude 127.03636666 · 공식 예제의 42dot |
| M 추가 경유지 | latitude 37.41275833 · longitude 127.09481944 · 공식 예제의 소프트웨어드림센터 |
| 시작 조건 | D 확인·FIRST/SECOND 경유지 없음·정차·다른 미확정 작업 없음 |
| 식별 기준 | 저장한 D·M·경유지 슬롯·기준 경로 관측. 좌표 비교 허용차는 각 축 0.00001 이하를 초기 시험값으로 사용 |

[공식 Waypoints 예제](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/NaviHelper/waypoint-settings)의 좌표를 호출·조회·정리 시험용으로 사용한다. Navigation 앱에서 D를 먼저 준비하고 조회로 확인한다. 실제 경로가 다르거나 슬롯이 이미 차 있으면 덮어쓰지 않고 준비 실패로 둔다. 이 코스의 실제 시간·경로를 강릉 ETA·7분 우회의 근거로 표시하지 않는다.

앱은 자기 시험에서 추가한 M만 제거한다. 다른 경유지로 바뀌었다면 자동 삭제하지 않고 경로 확인 필요로 둔다. 초기화를 위해 `removeWaypoint(ALL)`이나 `cancelRoute()`로 전체 사용자 경로를 지우는 구현은 하지 않는다.

### 8.3. attempt 기록과 물리 호출

| 필드 | 규칙 |
|---|---|
| `attemptId`, `operation` | 매 추가·제거마다 새 ID와 add/remove. 재시도는 이전 작업을 덮지 않음 |
| `source` | `real / mock`. add는 승인한 설정 모드, remove는 원래 add의 출처로 생성·고정. 재시도·표시 모드 전환으로 기존 시도의 출처를 바꾸지 않음 |
| 연결 정보 | storeId·runId·proposalId·deviceId·vehicleSessionId·승인 버전·대상 좌표·슬롯 |
| `dispatch` | `not_started / may_have_executed / settled`. SDK 호출 직전에는 may_have_executed를 영속 저장 |
| `outcome` | `pending / applied / removed / failed / unknown / not_dispatched`. mock은 결과값이 아니며 source로 구분 |
| 관측 | real은 실제 observationSeq·D/M 조회·콜백·오류·근거, mock은 별도 mockRoute·모의 결과 기록. 서로의 근거로 대체하지 않음 |
| 정리 | cleanupRequired·원래 목적지 확인 여부·초기화 대상 여부 |
| `resolution` | `unresolved / reconciled / recovered_baseline`. unknown 이력을 지우지 않고 처리 종료·검증된 환경 복구 여부를 별도 보관 |

아래 물리 호출 절차는 source=real에 적용한다. source=mock은 8.5절의 모의 처리로 진행하며 실제 SDK 실행권·물리 호출 기록을 만들지 않는다.

1. A가 `NAV_APPROVE`를 확인하면 서버가 승인한 제안·차량에 묶인 source=real·not_started 작업을 저장한다. 조회만으로 SDK를 실행하지 않는다.
2. 같은 사용자 동작의 정상 응답 흐름에서 차량이 제한·활성·회차·현재 제안을 다시 확인하고 `NAV_DISPATCH_BEGIN`으로 실행 자격을 확인한다.
3. 서버가 해당 시도의 실행권을 한 번 부여한다. 차량은 로컬 실행 기록에 may_have_executed를 저장하고 동기 저장 성공을 확인한 뒤에만 SDK를 호출한다. 로컬 기록 실패 시 호출하지 않는다.
4. 실제 호출 직전에도 로컬 제한을 확인한다. 실행하지 않았음이 확실하면 not_dispatched로 보고한다. 충돌·종료·크래시로 불확실하면 unknown으로 두고 자동 반복하지 않는다.
5. 실제 요청 뒤 callback·목적지·경유지 조회를 대조해 결과를 `NAV_REPORT`로 보고한다. 통신 실패 시 같은 사실 보고를 재전송할 수 있지만 SDK를 다시 호출하지 않는다.

실행권 응답이 유실·시간 초과되면 원래 사용자 동작의 실행 흐름을 중단한다. 영수증 조회나 늦은 응답을 받은 것만으로 물리 호출을 재개하지 않는다. 로컬 실행 여부와 실제 경로를 확인한 뒤, 미실행이 확실하면 기존 작업을 종료하고 새 사용자 승인으로 다시 시도한다.

앱·서버의 기록만으로 물리 SDK 호출의 ‘정확히 한 번’을 보장한다고 설명하지 않는다. 호출 직전 크래시와 직후 크래시를 구분하지 못하면 재실행 대신 실제 상태를 조회한다. 앱 재시작·서버 재시작·화면 복원·명령 영수증 재수신은 새 SDK 실행 계기가 아니다.

서버의 최종 확인과 실제 SDK 호출 사이에 취소가 도착할 수 있다. 이를 완전히 없앴다고 가정하지 않는다. 만남 취소는 유지하며, 뒤늦게 M이 추가되면 제거 필요로 전환한다. 실행권을 한 번 받았더라도 취소된 만남을 다시 확정하지 않는다.

### 8.4. 결과 판정·취소·복구

추가 성공은 **원래 D 유지 + 승인한 M 존재 + 해당 작업의 처리 완료 근거**를 확인한 경우다. 이벤트 하나만으로 현재 시도의 성공을 단정하지 않는다. SDK가 attemptId를 콜백에 돌려준다고 가정하지 않으며 실제 물리 작업은 한 번에 하나만 진행한다.

취소 시점의 기준은 SDK 경유지 추가 작업이다. 서버 승인 요청이 저장됐어도 실제 호출 전이며 실행되지 않았음이 확인되면 ‘요청 전’, SDK 호출 뒤 결과 확인 전은 ‘처리 중’, D 유지·M 추가가 확인되면 ‘반영 후’다. 실행 여부가 불확실하면 요청 전으로 간주하지 않고 unknown 확인 절차를 따른다. 만남 시작 전 취소는 meeting=cancelled이며, 실제 만남 뒤의 MEETING_END/meeting=ended와 구분한다.

| 상황 | 서버·차량 처리 |
|---|---|
| 추가 요청 반환·라우팅 시작 | pending. 성공 표시 없음 |
| D 유지·M 반영·완료 확인 | applied. 실제 근거 저장 뒤에만 내비 반영 완료 |
| 오류·M 미반영·해당 처리 종료 확인 | failed. 새 운전자 확인으로 새 attempt 재시도 가능 |
| 출처 불명 오류·10초 판정 불가 | unknown. 상태 조회·복구 우선, 추가·모의 전환·새 실제 회차 잠금 |
| 요청 전 취소 | 아직 실행되지 않은 작업 무효화. 물리 실행이 없음을 확인 |
| 요청 중 취소 | meeting=cancelled 유지. 결과 보고는 받아 M 존재 여부 확인 |
| 취소 후 추가 성공 | applied 사실과 cleanupRequired를 함께 기록. 만남 시작·최종 선택 금지 |
| 추가 완료 후 취소 | 제거 제안·운전자 승인 후 별도 remove attempt. 자동 삭제 금지 |
| 제거 결과 | M 없음과 처리 종료 확인 시 removed. D 유지가 미확인이면 경로 확인 필요 안내 유지 |
| 제거 실패·미확인 | 취소 유지·cleanupRequired 유지. 본인 대화로 가도 안내를 숨기지 않음 |
| 다른 경로·다른 경유지 발견 | 자기 작업이라고 추정해 수정하지 않고 recovery 필요 |

타임아웃 후 경유지가 한 번 보이지 않았다는 사실만으로 ‘미반영·처리 종료’를 확정하지 않는다. 이후 늦은 요청이 적용될 수 있으면 unknown이다. 여러 관측과 SDK 동작을 대조해 종료를 확인할 수 없을 때는 실제 모드를 미완료로 남기고 시험 환경을 복구한다.

SDK 리스너 결과는 현재 업무 version과 달라도 알려진 attempt의 사실로 기록한다. 취소·초기화·이전 회차 결과는 업무 동의를 되살리지 않지만 물리 경로에 영향을 줄 수 있으므로 버리지 않는다. 회차 밖 결과가 현재 경로와 충돌하면 현재 회차의 recovery를 잠근다. 임의의 미등록 attempt나 다른 장치의 결과는 반영하지 않는다.

`MockNaviAdapter`도 같은 동의·운전자 승인·취소 규칙을 사용한다. source=mock인 applied/removed/failed/unknown은 모의 결과이고 실제 SDK 증빙이 아니다. 실제 실패 후 NAV_MOCK_CONTINUE는 표시 모드만 바꾸며 실패한 source=real 작업·정리 기록을 보존한다. 이 동작으로 해당 real attempt를 NAV_MOCK_RESULT의 대상으로 바꾸거나 미확정 실제 작업을 지우지 않는다.

### 8.5. 모의 내비 결과·실패 주입 계약

모의 모드는 실제 내비를 호출하지 않는다. 초기 mockRoute는 가상의 기준 목적지 D·M 없음으로 준비한다. 유효한 운전자 NAV_APPROVE 또는 NAV_REMOVE_APPROVE 뒤에 서버가 source=mock·outcome=pending인 attempt를 만들고, MockNaviAdapter는 그 상태를 표시한다. 자동 성공 타이머·별도 가짜 NAV_REPORT를 만들지 않으며 O01의 NAV_MOCK_RESULT로 결과를 정한다. 대표 모의 시연에서도 추가·필요한 제거에 대해 시연자가 각각 결과를 지정한다.

| 요소 | 계약 |
|---|---|
| 명령·역할 | NAV_MOCK_RESULT, operator 전용. 일반 사용자·car 역할은 결과를 지정할 수 없음 |
| 대상 | target.attemptId·operation=add/remove. 현재 run의 알려진 source=mock 시도이며 해당 시도에 기록한 원래 승인·제안/정리 사유와 일치해야 함 |
| 결과 | payload.outcome=applied/removed/failed/unknown. add에는 applied, remove에는 removed만 성공값으로 허용 |
| 적용 가능 상태 | 현재 pending 또는 unknown. 이미 확정된 applied/removed/failed/not_dispatched에는 새 결과로 덮어쓰기 금지 |
| 성공·실패 | applied는 mockRoute에 M 존재, removed는 M 없음으로 반영. failed는 해당 작업 미반영·종료를 기록하고 직전 모의 경로 유지. 처리 종료는 dispatch=settled |
| 미확인 | unknown은 mockRoute의 마지막 확인값을 유지하고 해당 작업의 반영 여부를 미확인으로 표시. 재시도·만남 시작 차단, 후속 모의 결과 지정으로만 해소 |
| 재시도 | failed·미반영·처리 종료가 확인되고 만남/정리 사유·새 운전자 승인이 유효할 때 새 source=mock attempt 발급. unknown에서 새 시도 금지 |
| 중복·버전 | 공통 expectedVersion·commandId·영수증 규칙 적용. 같은 전송은 재적용하지 않고, 다른 회차·대상·확정 시도에 대한 변경은 거부 |
| 취소·초기화 | 알려진 미완료 mock 시도의 늦은 결과는 현재 run에서 정리 목적으로 받을 수 있음. 만남 취소/초기화는 유지하며 새 동의·장면 전환을 만들지 않음 |

주행 제한 중 도착한 모의 결과도 상태 기록만 갱신한다. 실제 제한을 해제하거나 만남 시작·다음 선택으로 자동 진행하지 않는다. 취소 뒤 applied면 모의 M 정리가 필요하며, 주차·운전자 제거 승인 후 새 remove attempt와 별도 결과 지정으로 정리한다. unknown 해소 전 전체 초기화 완료로 기록하지 않는다.

모의 unknown은 해당 모의 작업·만남 진행을 잠그며 실제 SDK recovery나 실제 경로 관측을 새로 만들지 않는다. 나중에 유효한 모의 결과로 해소해도 unknown 이벤트와 출처는 기록에 남긴다. 모의 작업과 별개로 기존 real 이력의 정리·복구 잠금이 있으면 그대로 유지한다.

모의 제거 실패의 재시도도 이전 remove attempt를 참조한 새 운전자 확인으로 발급한다. 자기 정리 대상임을 확인하면 만남 취소·초기화 중에도 가능하며 새 만남을 요구하지 않는다. 모든 모의 결과는 source=mock과 함께 저장·표시하고 realNaviVerified·실제 경로 관측·실제 SDK 통과 증빙을 갱신하지 않는다.

## 9. 상태 동기화·재시연·전체 초기화

### 9.1. 영속 저장과 재시작

서버의 상태·영수증·내비 journal은 업무 전환과 함께 저장한다. 선택 초안·펼침·자막 위치는 서버 성공값으로 복구하지 않는다. 서버 재시작은 같은 runId·runSeq를 읽되 차량 세션·heartbeat를 만료시키고 version을 증가시켜 다시 확인하게 한다. 이전 세션을 현재 차량 활성 상태로 인정하지 않는다.

차량은 실행 기록을 앱 전용 저장소에 동기 저장한다. attempt·승인 대상·may_have_executed·마지막 관측을 재시작 후에도 대조한다. 서버에 미정리 기록이 있는데 차량 기록이 없거나 그 반대이면 recovery 필요다. 새 저장소·새 앱 설치로 실제 내비가 정리됐다고 간주하지 않는다.

SDK 호출·정리 사실은 회차 밖 journal에 보존하고 관련 영수증도 회차와 묶어 유지한다. 전체 초기화는 사용자 시연 데이터를 새로 시작하는 것이지 미확정 외부 효과의 증거를 삭제하는 기능이 아니다.

### 9.2. 최종 선택만 재시연

만남 종료 직후 최종 선택 전의 `finalCheckpoint`를 저장한다. 완료된 만남·storyConnectionId와 표시용 이야기 참조만 보관한다. 현재 profile/publicApproval·connection·trip·nav·recovery·차량 세션/제한·version·실행권·미처리 메시지/통화 요청은 과거 값으로 덮어쓰지 않는다.

`REPLAY_FINAL`은 다음을 수행한다.

1. 만남 종료·유효한 S12 결과·초기화/복구 잠금 없음을 확인한다.
2. finalRound를 증가시키고 새 finalId를 발급한다. A/B 선택은 null·결과 pending·활성 requestId=null로 두며, 이전 B 요청은 종료 이력으로 보존한다. 이유·후기·장식 변경을 초기화한다.
3. replayContext.mode를 final_replay로 두고 checkpointId·storyConnectionId로 발표용 최종 선택 맥락만 연다. 이미 닫힌 live connection은 closed로 유지하고 철회한 공개 승인도 복원하지 않는다. A 선택을 기다리고 together일 때만 새 B requestId를 발급한다. 이때 B 최종 응답은 live linked가 아닌 유효한 checkpoint·새 round·현재 활성 요청을 조건으로 검증한다.
4. 재시연 중에는 최종 선택·해당 B 응답·결말 표시와 필요한 관리/사실 보고만 허용한다. UI뿐 아니라 서버가 새 메시지·통화·만남·SDK 추가를 거부한다. 이전 대기 요청을 살리지 않는다.
5. 이전 finalRound·requestId의 늦은 응답을 거부한다. 원래 프로필·만남 전제·실제 내비 기록은 유지한다.

final_replay의 기본 업무 허용 목록은 FINAL_CHOOSE·해당 B_RESPONSE(kind=final)다. 추가 기능 채택 시 확정된 새 round의 결말 조건·capabilities를 만족하는 SAVE_REASON·TRIP_FINISHED·REVIEW_APPLY/REVIEW_SKIP만 추가한다. REPLAY_FINAL·RESET_BEGIN/ACK·차량 재접속/상태/기존 ACK·SDK 사실/기존 모의 결과·필요한 정리·공개 철회/연결 종료 같은 관리·중단은 각 원래 조건으로 처리할 수 있다. 이를 이유로 새 HANDOFF_PREPARE·CONNECT_REQUEST·MESSAGE_SEND·CALL_PROPOSE·MC_PROPOSE·MEETING_PROPOSE·NAV_APPROVE나 추가용 NAV_RETRY를 열지 않는다. 정리 목적 remove 재시도는 현재 정리 사유로만 허용한다.

만남 전 종료·공개 보류·연결 거절에는 checkpoint가 없으므로 최종 재시연을 열지 않는다. 사용자가 본인 일정을 펼쳤더라도 같은 S12 결과·checkpoint가 유지되는 범위에서는 시연자가 선택 직전으로 돌아갈 수 있다.

### 9.3. 전체 초기화

`RESET_BEGIN`은 새 업무 행동을 막고 resetId를 발급한다. 기존 회차를 즉시 삭제하거나 새 runId를 먼저 발급하지 않는다. 미전송 초안·음성·예약 B 이벤트를 정리하고 각 클라이언트에 초기화 대기를 표시한다.

| 참여·작업 이력 | 완료에 필요한 조건 |
|---|---|
| 웹만 사용·차량 불러오기 없음·실제 SDK 이력 없음 | 서버 요청 정리와 연결된 웹의 UI 정리 ACK |
| 차량이 전달본을 불러온 회차 | 서버 정리 + 해당 차량의 UI·음성·대기 요청 정리 ACK |
| 모의 내비 작업 이력 존재 | pending/unknown 결과 확인·모의 M 정리와 차량 ACK. 모의 정리는 실제 D/M 확인·SDK 정리 증빙으로 사용하지 않음 |
| 실제 SDK 승인·작업 이력 존재 | 실행 차량과 원래 목적지·추가 경유지·미확정 작업을 대조해 외부 정리 확인 |
| 실제 시도 unknown·기록 불일치 | needs_recovery 유지. 새 실제 회차 금지, 모의 전환으로 정리 완료 처리하지 않음 |

실제 경로를 바꾸는 정리는 주차·상태 확인과 운전자 승인 또는 검증된 시험 정리 절차를 따른다. M만 제거하고 D·기준 경유지 목록을 확인한다. 처리 중 호출이 나중에 M을 추가할 가능성이 남으면 완료 ACK를 보내지 않는다.

초기화의 제거 승인은 reason=reset_cleanup과 현재 resetId·원래 add attempt를 사용한다. 만남이 confirmed/ended 상태여도 자기 시험 경유지 정리가 가능하며, 그 목적 때문에 만남을 cancelled로 조작하지 않는다. 같은 deviceId의 재접속 후 현재 세션이 경로·미처리 기록을 확인해 RESET_ACK한다. 초기화 정리 화면은 일반 업무 잠금 중에도 접근 가능하지만 실제 제한 중 새 경로 변경은 허용하지 않는다.

필요한 ACK와 실제 경로 확인을 모두 받으면 runSeq를 증가시키고 새 runId·기본 비공개 프로필 상태·새 요청 공간을 저장한다. 그 뒤 클라이언트가 M01부터 시작한다. 이전 요청의 응답은 무효이며 알려진 실제 SDK의 늦은 사실 보고는 journal·recovery 검증에만 사용한다.

새 회차에서는 차량 세션·heartbeat도 미확인으로 바꾸고 현재 회차에 다시 연결하게 한다. 이전 세션 보고로 조작을 열지 않는다. 알려진 이전 attempt의 SDK 사실 보고는 이 세션 갱신과 별개로 journal에 남긴다.

클라이언트가 꺼져 ACK를 못 받으면 자동으로 완료하지 않는다. 재접속·현재 상태 확인으로 이어가며, 로컬 UI 상태만 사라졌다는 이유로 외부 내비 정리를 생략하지 않는다. 에뮬레이터 재시작을 사용한 복구도 실제 목적지·경유지 재조회 후 증빙한다.

### 9.4. 미확정 시험 환경 복구의 종료 조건

일반 SDK 재조회로 처리 종료·자기 경유지 정리를 확정할 수 있으면 해당 NAV_REPORT 근거로 resolution=reconciled를 기록한다. 경유지가 한 번 없다는 관측만으로 종료시키지 않는다. 이를 확인할 수 없을 때 환경 재시작 등을 검증된 복구 절차로 사용할 수 있으나, 재시작 버튼 자체를 성공 근거로 삼지 않는다.

W06에서 현재 SDK·에뮬레이터 조합에 대해 이전 실행 종료와 D/M 기준 재확인을 검증한 절차만 recoveryProcedureId로 등록한다. 검증된 절차가 없으면 허용 목록은 비어 있고 RECOVERY_CONFIRM도 비활성이다. 실제 모드는 미완료·복구 필요로 유지한다.

복구 확인 절차는 다음과 같다.

1. 새 추가 실행권과 예약 동작을 중단하고 자기 attempt·현재 resetId를 대조한다.
2. 등록된 절차에 따라 이전 실행이 더 진행되지 않는 근거를 확인한다. 같은 장치 재접속은 새 epoch로 등록하고 기존 실행 기록을 보존한다.
3. 현재 세션에서 D 일치·M 없음·다른 미처리 작업 없음·실제 제한 확인의 관측을 NAV_REPORT로 보내고 서버 evidenceId를 받는다.
4. O01의 RECOVERY_CONFIRM이 현재 evidenceId·대상 attempt·등록 절차를 대조한다. 누락·오래된 관측·다른 장치·살아 있는 실행권은 거부한다.
5. 충족한 attempt에 resolution=recovered_baseline을 기록한다. 원래 unknown/실패 outcome과 증빙은 보존하고 실제 applied/removed 성공으로 바꾸지 않는다. 남은 미정리 시도가 없을 때에만 해당 복구 잠금을 해제한다.

초기화 중이었다면 이 뒤에도 RESET_ACK가 필요하며 새 run은 정상 초기화 완료 절차로 발급한다. 복구 확인만으로 realNaviVerified를 true로 만들지 않는다. 등록할 수 있는 복구 절차·실제 SDK 동작은 아직 검증하지 않았으며 W06·W13·05번의 증빙으로 채운다.

## 10. 소재·빌드·실행 계약

### 10.1. 공통 소재

`assets-manifest.json`은 `assetId`, `kind`, `path`, `captionId`, `speaker`, `sourceKind`, `requiredPublicFields`, `styleVariant`를 연결한다. sourceKind는 `own_agent / peer_agent / peer_message_fixture / call_sample / meeting_reenactment`로 구분한다. 실제 사용자 메시지 재현은 원문 문장 ID와 발신자를 유지한다.

각 대사는 02번 2.3절의 cueId·requiresCueIds·fallbackCueId도 연결한다. 먼저 현재 공개 필드로 허용 대사를 거르고, 그다음 실제 표시 이력·표현에 맞는 변형을 선택한다. 이력이 없거나 누락되면 일반 대사로 간다. requiresCueIds는 본인/상대 대화가 실제 제공됐는지의 로컬 이력이며 동의·실제 열람·성향 추론의 증빙으로 사용하지 않는다. 회차·연결이 바뀌면 이력을 지우고, 이력 확인이 안 되면 보수적으로 일반 대사를 사용한다.

S10_MEETING_FAMILIAR는 추가로 storyContext.peerIntroSeen=true를 요구한다. A가 B의 Q1을 본 것과 B가 A 소개를 접했다는 이야기 전제를 서로 대신하지 않는다. 이 전제·현재 공개 필드·선행 cue 중 하나라도 없으면 MEETING_HELLO_GENERAL로 간다. S08의 A 인사 조건에는 B의 사전 소개 전제를 추가하지 않는다.

웹·차량은 같은 manifest와 PNG·MP3를 사용하고 `sync-assets`가 차량 assets로 복사한다. A 외형을 임의 기본값으로 바꾸지 않으며 누락은 기록한다. 음성 누락은 자막으로 진행하고, 필수 캐릭터·대사 데이터 누락은 명시적 오류로 남긴다. MC·후기·이유 입력은 capabilities와 소재 유무가 일치할 때만 활성화한다.

### 10.2. 구현 후 실행할 명령

다음 Node 명령은 `mock-app/`의 서버·테스트·소재 동기화를 구현한 뒤의 실행 계약이다. 현재 해당 Node 명령은 제공하지 않는다.

```sh
npm run sync-assets
npm test
npm start
```

`package.json`에는 구현 시 start=`node server/main.mjs`, test=`node --test`, sync-assets=`node scripts/sync-assets.mjs`를 정의한다. Android는 `mock-app/vehicle`을 열고 Gradle 동기화·에뮬레이터 실행·설치를 확인한다. 현재 mock 빌드·Lint는 제공하며 real 빌드는 SDK 준비 후 추가할 목표다.

```sh
./gradlew assembleMockDebug
./gradlew lintMockDebug
# 다음 명령은 아직 제공하지 않는 실제 SDK 연결 목표다.
./gradlew assembleRealDebug
```

real 빌드는 사전 SDK 검증 단계이며 mock 성공이 real 성공을 뜻하지 않는다. 포트·API 주소·Node·Android Studio·JDK·AGP·Gradle·Emulator·SDK·실제 권한·모드·시험 코스를 `runtime/verification.json`에 기록한다.

### 10.3. 첫 연동 순서

1. 서버·웹·차량에서 `/health`·schemaVersion을 확인한다.
2. 온보딩의 별명·외형·표현을 기본값과 다르게 저장하고 공개·비공개 소개를 각각 확인한다.

4. 공개 보류 또는 연결 종료 → my_trip 전달 → 내 에이전트 진입도 확인한다.
5. 실제 제한 읽기·만료·복귀와 무음 진행을 확인한다.
6. 작은 real 시험에서 SDK 초기화·D/M 조회·추가·취소 후 제거·재시작 기록을 검증하고 실제 모드 사용 가능 여부를 결정한다.
7. 그다음 02번 전체 시연·두 결말·재시연을 연결한다. 화면을 모두 만든 뒤 처음 통신을 시도하지 않는다.
