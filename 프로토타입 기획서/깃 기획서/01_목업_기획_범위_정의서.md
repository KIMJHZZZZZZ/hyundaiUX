# wayMate 목업 기획 및 범위 정의서

작성일 2026년 11월 10일 · 수정일 2026년 11월 11일 · 버전 0.6 · 팀 공유용 수정안

**wayMate는 나를 알아가는 캐릭터 에이전트와 자동차 여행을 하며, 일정과 취향이 맞는 여행자와 자연스럽게 가까워지는 서비스다.** 모바일에서 에이전트와 대화하며 나와 여행에 관한 정보를 준비하고, 차량에서는 상대의 캐릭터를 통해 서로를 알아간다. 잠깐 만난 뒤에는 함께 여행하거나 내 캐릭터와 본인의 여정을 이어갈 수 있다.

개발 가제는 `wayMate`이며, 기존 자료의 ‘말문이 트립’은 서비스 가칭이다. 최종 서비스명은 별도로 결정한다.

이 문서는 기획·디자인·개발·PM이 공유할 서비스 방향과 **시나리오 중심 목업의 제작 범위**를 정한다. 상세 대본은 02번, 화면과 버튼 동작은 03번, 코드 구성과 연동 방법은 04번, 담당·일정·검수는 05번 문서에서 구체화한다.

문서에서 A는 시연자가 조작하는 주인공, B는 연결 상대다. 내 에이전트는 A의 친구이고 상대 캐릭터는 B를 소개하는 캐릭터다. ‘대화 연결’은 서로 알아갈 수 있게 된 상태, ‘만남 확정’은 같은 장소·시간에 만나기로 합의한 상태, ‘함께 여행’은 만난 뒤 남은 활동을 함께하기로 선택한 결과다. 같은 차량에 동승한다는 뜻은 아니다. 목업은 이 경험을 직접 눌러 확인하는 시제품이며, 준비된 대사·일정으로 진행하는 부분과 실제 정보 저장·전달을 구분한다.

## 2. 사용자의 상황과 해결할 문제

주인공은 혼자 여행의 일정과 속도를 유지하면서, 취향이 맞는 사람과 잠깐 이야기하거나 활동을 함께하고 싶다. 낯선 사람과 바로 통화하거나 만나는 것은 부담스럽고, 동행하지 않더라도 자신의 여행이 즐겁게 이어지기를 바란다.

| 사용자의 부담 | wayMate가 제안하는 경험 |
|---|---|
| 설문 항목만으로 나의 취향과 대화 방식을 설명하기 어렵다. | 내 에이전트와 편하게 대화하고, 정리된 프로필과 캐릭터의 표현 방식을 확인한다. |
| 여행 계획을 등록해도 누구와 만날 수 있을지 직접 비교하기 어렵다. | 에이전트가 목적지·시간·이동 부담·공통 관심사를 함께 고려한 후보와 추천 이유를 제안한다. |
| 처음부터 상대와 직접 대화하기는 어색하다. | 상대의 캐릭터와 먼저 대화하며 알아가고, 원하는 콘텐츠를 선택해 친밀도를 높인다. |
| 만나기 위해 자신의 일정이나 상대의 일정을 크게 바꾸고 싶지 않다. | 두 사람의 경로와 일정에 맞는 공개 장소를 제안하고 양쪽 동의 후 이동에 연결한다. |
| 만남 이후 계속 동행해야 할 것 같거나, 혼자 남는 느낌이 든다. | 함께 이어가기와 내 캐릭터와 이어가기를 모두 자연스러운 여행의 결과로 제공한다. |

이는 목업에서 확인할 사용자 상황과 설계 가정이다. 대화형 온보딩이 더 정확한 이해를 돕는지, 캐릭터를 통한 사전 대화가 실제 만남의 어색함을 줄이는지는 후속 사용자 검증 대상으로 둔다. 시장 규모·수요·효과를 수치로 설명할 때는 별도의 근거를 붙인다.

기능이 동작하는지 확인하는 Q 검수와, 사용자 가치·실현성을 확인하는 V 검증을 구분한다. 05번 V01~V05는 방문 캐릭터와 프로필 카드의 비교, 내 친구의 동행감, 늦은 상대 응답, 만남의 전체 시간 부담, 실제 주행 중 경험의 실현성을 다룬다. 대본의 ‘익숙하다’는 반응이나 모의 내비 성공만으로 이 가설이 확인됐다고 판단하지 않는다. 구체적인 표본·정량 판정 기준·실행 담당자·마감은 미정이고 결과는 미실시다.

## 3. 서비스의 핵심 경험

### 3.1. 대화로 나를 알아가는 내 에이전트

초기 가입 이후의 성향·취미 설문을 에이전트와의 채팅으로 구성한다. 에이전트는 “쉬는 날에는 뭘 하면서 보내?”, “여행에서는 한 곳에 오래 머무는 편이야?”, “처음 만난 사람과는 어떤 이야기가 편해?”처럼 답하기 쉬운 질문을 이어간다. 하단 자유 입력 채팅창이 기본이다. 사용자는 자기 문장과 말투로 답한다. 예시 답변 칩은 선택 사항이며 누르면 입력창에 초안만 채운다. 사용자는 고치거나 지울 수 있고, 전송 버튼을 눌러야 답변이 전송된다. 예시를 선택하지 않아도 진행할 수 있다.

목표는 사용자가 직접 설명한 관심사뿐 아니라 문장 길이, 자주 쓰는 표현, 농담과 대화 속도에 대한 선호 등 캐릭터 표현에 필요한 단서를 얻는 것이다. **텍스트 채팅에서 확인할 수 있는 표현 습관과 음성 입력이 있어야 관찰할 수 있는 말의 속도·억양·쉼을 구분한다.** 텍스트만으로 실제 음성의 특징이나 표정·몸짓을 파악했다고 표현하지 않는다. 짧은 대화에서 추정한 특징은 확정된 성격으로 단정하지 않는다.

대화가 끝나면 관심사·여행 성향·대화 스타일을 “내가 이해한 너”라는 요약과 캐릭터의 소개 예시로 보여준다. 본인 요약 확인과 상대 공개 승인을 구분한다. 공개를 보류해도 본인 요약·내 친구·여행 준비와 차량 이어받기는 유지한다. 원문 대화 전체가 상대 캐릭터에게 전달되는 구조로 만들지 않는다.

예를 들어 사용자가 “바다 보면서 멍때리다가 카페 가는 게 좋아 ㅋㅋ”라고 답하면, 캐릭터가 “파도는 바다 보면서 느긋하게 쉬는 걸 좋아해. 커피 한 잔도 빠질 수 없대 ㅎㅎ”처럼 소개하는 예시를 보여준다. 표현 방식은 사용자가 확인한 범위에서 반영하며, 실제 사람이 말한 문장과 캐릭터가 구성한 소개는 구분한다.

다른 여행자와 연결할 때는 별명·캐릭터와 여행 권역·공통 시간의 공개 확인이 필요하다. 관심사·성향·표현 공개는 선택이다. 이를 제외하면 추천·소개·만남 대사에서 해당 공통 취향을 단정하지 않고 시간·이동 부담으로 설명한다. 표현을 공개하지 않은 방문 캐릭터는 중립 소개를 사용한다. 내 친구는 본인에게만 말할 때 본인이 확인한 비공개 취향을 사용할 수 있다. 조건별 실제 대사는 02번을 따른다.

### 3.2. 여행 희망을 이해하고 먼저 제안하는 추천

사용자가 “주말에 강릉 쪽으로 가서 바다도 보고 카페에도 가고 싶어”처럼 여행 희망을 공유하면, 에이전트가 활동 권역·날짜·가능 시간·다음 일정·복귀 마감을 확인하고 여행 계획으로 정리한다. 장소와 시간처럼 정확한 값이 필요한 항목은 채팅 안의 간단한 선택·확인 요소로 보완한다.

일정의 각 시각은 아래처럼 구분한다. **만날 수 있는 시간 범위 전체를 상대와 함께 보내는 것은 아니다.** 대표 시연의 복귀 장소는 각자가 정한 강릉권 숙소이며, 정확한 주소는 상대에게 공개하지 않는다.

| 일정 용어 | 뜻 | A의 대표 예시 |
|---|---|---|
| 만남 가능 시간 | 다른 여행자와 만남·활동을 잡을 수 있는 본인의 여유 시간 | 13:00~15:00. 두 시간 내내 만나는 약속이 아님 |
| 공통 가능 시간 | A와 B의 만남 가능 시간이 겹치는 범위 | 14:00~15:00. 아직 특정 만남이 확정된 것은 아님 |
| 확정된 첫 만남 | 공통 시간 안에서 양쪽이 따로 합의한 약속 | 카페에서 14:15~14:35, 20분 |
| 기존 다음 일정 | 연결 전부터 본인 여행에 있던 별도 일정 | 15:20 기존 개인 방문지 도착. 매칭으로 새로 생긴 일정이 아님 |
| 숙소 도착 예상 | 만남·활동과 기존 다음 일정을 거쳐 본인 숙소에 도착할 계획상 시각 | 15:45. 실제 교통으로 계산한 실시간 도착 예정은 아님 |
| 숙소 도착 마감 | 본인이 숙소에 늦어도 도착하고 싶은 시각 | 16:00. 다음 방문지에 도착할 마감이나 만남 종료 시각이 아님 |

데이터의 기존 이름인 ‘복귀 예상·복귀 마감’은 위의 숙소 도착 예상·마감을 뜻한다. 다른 여행에서는 사용자가 정한 복귀 장소를 기준으로 해야 하며, 출발지·집·다음 방문지를 자동으로 복귀 장소로 간주하지 않는다.

소개·여행 요약 공개를 승인하고 계획을 저장하면 시스템이 후보를 준비하고 에이전트가 추천을 알린다. 공개를 보류하면 본인 여행으로 이어간다. 추천 근거는 다음과 같다.

- 비슷하거나 함께 방문할 수 있는 활동 목적지와 권역
- 겹치는 활동 시간과 각자의 경로에서 추가되는 이동 부담
- 공통 취미·활동, 여행 속도와 대화 스타일
- 두 사람 모두 다음 일정과 복귀 시한을 지킬 수 있는지 여부

후보 카드의 비교 기능은 유지하되, 에이전트가 “솔바람도 바다 산책과 카페를 좋아하고, 같은 시간대에 강릉에 있어. 네 일정에서 추가 이동은 7분 정도야”처럼 제안의 이유를 설명한다. **정보 확인 → 조건 비교 → 이유를 담은 제안 → 사용자가 선택한 다음 행동 준비**의 흐름으로 에이전트의 역할을 드러낸다. 연결 요청과 수락은 사용자가 결정한다.

### 3.3. 상대의 캐릭터를 통해 먼저 익숙해지는 이동 시간

서비스는 각자 운전하는 이동 시간을 서로 알아가는 시간으로 활용하는 것을 지향한다. A의 차에는 B의 캐릭터가, B의 차에는 A의 캐릭터가 방문해 주인의 공개 관심사와 확인된 표현 방식을 바탕으로 대화한다. 실제로 만났을 때 대화 주제와 표현이 조금 익숙하게 느껴지는 경험을 목표로 한다.

상대 차에 등장하는 캐릭터는 공개를 승인한 정보로 대화하는 방문 캐릭터다. 내 에이전트와의 관계와 기억은 내 쪽에 유지되며, 상대에게 비공개 대화나 전체 개인 일정이 넘어가지 않는다. 상대 캐릭터와 대화하는 동안에도 내 에이전트로 돌아갈 수 있다.

콘텐츠의 목적은 **상대를 알아가고 서로의 대화가 편하게 이어지도록 돕는 것**이다. 가벼운 여행 이야기, 취향 질문, 밸런스 게임처럼 부담 없이 스몰토크를 시작할 수 있는 방식으로 확장할 수 있다. 서비스 전체의 콘텐츠 목록을 아래 항목으로 고정하지 않는다. 이번 목업에서는 제작·검수가 가능하도록 아래 대표 방식을 정하고, 사용자가 고르거나 건너뛰고 종료할 수 있게 한다. 모두 순서대로 수행해야 만날 수 있는 구조로 만들지 않는다.

| 콘텐츠 | 사용자 경험 | 이번 목업 |
|---|---|---|
| 상대 캐릭터와 알아가기 | 상대의 취미·여행 스타일에 대해 편하게 질문하고, 주인을 닮은 표현의 답변을 듣는다. | 필수 · 준비된 질문·답변과 음성으로 한 장면 이상 재현 |
| 에이전트로 말 전하기 | 사용자가 선택·확인한 질문이나 말을 상대에게 전달하고, 상대가 보낸 답변을 듣는다. | 필수 · 질문 전달과 B의 답변 수신 한 차례 재현 |
| 둘이 직접 통화하기 | 두 사람이 원할 때 에이전트 대화에서 실제 사람 간 대화로 넘어간다. | 필수 · 선택·동의·종료 UI와 통화 샘플 음성 재현, 실제 통신은 후속 |
| 에이전트 MC와 통화하기 | 두 사람의 통화에 동의받은 MC 에이전트가 참여해 공통 주제를 꺼내거나 대화를 돕는다. | 추가 · 짧은 콘셉트 장면, 실제 다자 통화는 후속 |
| 여행 취향 밸런스 게임 등 | ‘바다 산책 vs 카페에서 쉬기’처럼 정답 없는 질문으로 대화 주제를 만든다. | 확장 아이디어 · 제작 채택 미정. 이번 필수 구현·시연 시간에는 추가하지 않음 |

상대 캐릭터가 공개 프로필을 바탕으로 답한 말과 상대 사용자가 직접 보낸 말은 발화자 표시와 표현으로 구분한다. 예를 들어 “솔바람은 조용한 카페를 좋아해”는 캐릭터 소개이고, “솔바람이 방금 ‘바다 산책 좋아요’라고 답했어”는 실제 사용자 응답을 전달하는 장면이다. 목업에서는 후자도 B의 대본 이벤트임을 시연 자료에 표시한다. 캐릭터는 알지 못하는 개인 사실을 만들거나 주인의 현재 의사·동의·만남 약속을 대신 확정하지 않는다.

콘텐츠 목록은 후속 업데이트로 확장할 수 있게 구분한다. 이번에 제공하지 않는 콘텐츠는 ‘준비 중’으로 표시하고 실행 가능한 기능처럼 보이지 않게 한다. 주행 중 음성 경험의 목표와 실제 Pleos 지원·목업 재현 방식은 7절에서 구분한다.

이런 질문에 상대 캐릭터가 답할 때는 공개를 승인한 취향만 소개한다. 실제 상대의 지금 선택을 듣고 싶으면 문장을 확인해 전달하거나 양쪽 동의 후 통화한다. 캐릭터의 답변으로 상대가 게임에 참여했거나 같은 선택을 했다고 꾸미지 않는다.

### 3.4. 두 사람의 여정에 맞는 짧은 만남 제안

사용자가 ‘만남 제안 받기’를 선택하면 에이전트가 두 사람의 경로와 일정, 공개된 공통 관심사에 맞춰 잠깐 만날 장소를 제안한다. 앞선 대화를 모두 완료할 필요는 없다. 단순히 두 위치의 지리적 중간을 고르는 대신, **양쪽의 추가 이동·도착 시각·체류시간·다음 일정·복귀 여유를 만족하는 장소**를 우선한다. 그 안에서 분위기, 조용함, 바다 전망 등 공개 취향에 맞는 이유를 설명한다.

예를 들어 “두 사람 경로에서 조금만 들르면 되는 바닷가 카페가 있어. 조용한 분위기를 둘 다 좋아하니까 여기서 20분 정도 만나볼래?”라고 제안한다. 장소 카드에는 공개 장소명, 만남 시각·체류시간, 본인의 추가 이동시간과 양쪽 일정 충족 여부를 함께 보여준다. 실제 서비스의 장소 후보에는 공개 접근·주차·이용시간 확인이 필요하며, 이번 목업은 이를 만족한다고 설정한 가상 장소 한 곳을 사용한다.

추가 주행이 짧다는 이유만으로 만남의 전체 부담이 작다고 단정하지 않는다. 대표 카드에는 A의 도착 후 대기 13분·첫 만남 20분·이후 산책 20분은 별도 선택임을 함께 보여준다. 원래 카페·해변 활동을 대신하는 만남인지 추가 일정인지는 V04에서 확인한다. 두 사람이 제때 정차·응답할 수 있다는 대표 이야기의 가정과 늦은 응답 시의 서비스 기준은 V03에서 별도로 검증한다.

장소 추천, 두 사람의 만남 동의, 운전자의 내비 반영 승인은 각각 구분한다. 추천만으로 경로를 바꾸거나 수락을 대신하지 않는다.

### 3.5. 사람과 함께해도, 내 캐릭터와 이어가도 계속되는 여행

짧은 만남 뒤에는 ‘함께 여행 이어가기’와 ‘내 캐릭터와 여행 이어가기’를 선택한다. 한 사람이라도 각자의 여행을 원하면 상대와의 연결을 마무리하고 각자의 여정을 이어간다. 동행하지 않는 선택을 상대 평가나 매칭 실패로 표시하지 않는다. 이유 입력은 선택 사항이며 상대에게 전달하지 않는다.

내 캐릭터와 이어가는 결말에는 일정 안내에 더해, 온보딩에서 알게 된 취향을 다시 활용하는 짧은 대화와 다음 활동을 넣는다. 예를 들어 “아까 바다 보면서 쉬고 싶다고 했지? 다음은 네가 골라둔 해변이야. 이번엔 나랑 천천히 가보자”라고 말하며 원래 계획을 이어준다. 내 캐릭터와의 여행은 처음부터 제공되는 경험이며, 만남 전이나 연결을 종료한 뒤에도 이용할 수 있다.

두 결말 모두 의미 있는 여행 경험을 제공하되, 캐릭터 동행이 실제 사용자에게 충분한 만족을 주는지는 검증할 가정으로 남긴다.

## 5. 채널별 역할·정보·상태 기준

### 5.1. 모바일과 차량의 역할

모바일은 나와 여행을 설명하고 확인하는 준비 단계다. 차량은 이동 시간을 활용해 상대와 익숙해지고, 내 여정 안에서 다음 행동을 이어가는 접점이다. **모바일에서는 대화 연결과 가능 시간 확인까지, 만남 장소·시각의 합의는 차량 경험에서 진행한다.** 내 캐릭터와의 대화는 연결 여부와 무관하게 이어진다.

차량에 전달할 기준 정보는 본인의 프로필·캐릭터·여행 계획, 상대의 공개 프로필과 표현 스타일, 공통 가능 시간, 연결·콘텐츠·만남 상태다. 아직 합의하지 않은 만남 장소는 제안으로 표시한다. 같은 여행 ID와 상태 버전을 사용하고, 전송 실패·오래된 상태를 구분하는 방법은 04번에서 정한다.

전달 모드는 상대 연결을 포함한 `connected`와 본인 정보만의 `my_trip`으로 구분한다. 공개 보류·연결 종료 후에는 상대 없이 내 친구와 이어갈 수 있다. 재불러오기는 현재 상태를 복원하는 동작이며 이미 진행한 대화·만남·결말을 첫 소개로 되돌리지 않는다.

상대에게 공개할 정보는 별명·캐릭터·승인한 관심사와 소개 표현·활동 권역·공통 가능 시간이다. 만남이 확정되면 합의한 공개 장소·시각·체류시간을 함께 보여준다. 원문 온보딩 대화, 실명·전화번호·생년월일·차량번호·정밀 출발지·현재 좌표·숙소 주소와 전체 개인 일정은 상대에게 전달하지 않는다. 상대 일정은 ‘기존 일정 유지 가능’처럼 합의에 필요한 요약으로만 보여준다.

### 5.2. 상태와 동의

| 용어 | 의미와 다음 단계의 조건 |
|---|---|
| 공개 프로필 준비 | 사용자가 에이전트의 요약과 공개 범위를 확인한 상태다. |
| 후보 제안 | 여행 조건과 공개 프로필에 맞는 후보를 보여준 상태다. 상대와 연결되지는 않았다. |
| 대화 연결 완료 | 요청을 상대도 수락하고 가능한 날짜·시간대를 확인한 상태다. 통화·만남·여행 동행에는 별도 동의가 필요하다. |
| 콘텐츠 이용 | 사용자가 상대 캐릭터 대화 등 원하는 콘텐츠를 이용하는 상태다. 직접 메시지 전달·통화·MC 참여는 해당 행동에 필요한 확인·동의를 받는다. |
| 만남 확정 | 양쪽이 동일한 장소·시각·체류시간에 동의한 상태다. 이후 운전자가 내비 반영을 승인한다. |
| 함께 여행 이어가기 | 만남 이후 두 사람이 모두 남은 여행의 일부를 함께하기로 선택한 결과다. |
| 내 캐릭터와 여행 이어가기 | 한 사람이라도 각자의 여행을 선택해 상대 연결을 마무리하고 본인의 여행을 이어가는 결과다. |

상대 응답 대기 중에는 다음 단계가 확정된 것처럼 표시하지 않는다. 연결 요청 거절·연결 종료·만남 거절 시에는 상대와의 흐름을 마무리하고 내 캐릭터와 본인의 여정을 이어갈 수 있다. 통화 거절·건너뛰기는 통화만 생략한다. MC 참여에 동의하지 않으면 일반 통화를 선택할 수 있다. 장소·시각이 바뀌면 새 제안으로 다루고 이전 만남 동의를 재사용하지 않는다.

첫 만남 종료 때 A의 최종 선택을 준비하며 B의 응답은 아직 열지 않는다. A가 함께를 선택했을 때만 B도 최종 선택을 할 수 있다. A가 처음부터 내 친구와 이어가기를 선택하면 B 응답 없이 해당 결말로 간다. 재시연도 같은 순서이며 완료한 만남 기록은 연결 종료 때문에 취소 상태로 바뀌지 않는다.

### 5.3. 만남 취소와 내비 처리

여기서 ‘내비 요청’은 **기존 내비 목적지를 유지한 채, 만나기로 한 카페를 경유지로 추가해 달라는 요청**이다. 목적지를 처음 정하는 전체 절차나 일반 경로 검색의 전·중·후를 뜻하지 않는다. 예를 들어 ‘현재 위치 → 기존 다음 방문지’였던 안내를 ‘현재 위치 → 만남 카페 → 기존 다음 방문지’로 바꾸는 것이다. 만남 제안 → 양쪽 수락 → 주차 상태의 운전자 승인 → 경유지 추가 요청 → 반영 결과 확인 순서로 진행한다.

이번 목업은 기존 목적지가 이미 설정된 경우를 다룬다. 목적지가 없거나 준비한 경로와 다르면 먼저 확인하도록 안내하며, 앱이 임의로 목적지를 설정·덮어쓰지 않는다.

아래 취소는 **실제로 만나기 전 약속을 취소하는 경우**다. 20분간 만난 뒤 헤어지는 ‘만남 종료’와 구분하며, 취소한 만남에는 만남 후 동행 선택을 띄우지 않는다.

| 취소 시점 | 예시와 처리 |
|---|---|
| 경유지 추가 요청 전 | 아직 카페 추가 요청을 보내지 않았다면 약속과 상대 연결을 마무리한다. 기존 내비 안내는 그대로 두고, 경유지 추가·만남 후 동행 선택을 실행하지 않는다. |
| 경유지 추가 처리 중 | 요청은 보냈지만 반영 여부가 확인되지 않았다면 약속은 즉시 취소 상태로 둔다. 내비 요청까지 즉시 철회됐다고 가정하지 않고 결과를 확인한다. 늦게 추가 성공이 와도 약속을 되살리지 않으며, 카페가 남으면 제거 확인으로 이어간다. |
| 경유지 추가 반영 후 | 카페가 이미 경유지에 들어갔다면 약속 취소와 경유지 제거는 별개다. 주차 상태에서 운전자에게 ‘만남 카페를 빼고 기존 목적지로 계속 안내할까요?’라고 확인한 뒤 제거를 요청하고 결과를 확인한다. |

제거 실패·결과 미확인 시 ‘경유지 확인 필요’를 남긴다. ‘기존 목적지로 안내’는 카페 경유를 빼는 뜻이며, 차량이 이전 위치로 돌아가거나 과거와 똑같은 도로·도착 시각이 복원된다는 뜻은 아니다. 숙소에 도착했다는 뜻도 아니다.

목업에서는 위 상태와 실패 안내를 재현한다. 실제 경유지 추가·제거의 SDK 지원과 검증 결과는 04번에서 별도로 기록한다.

모의 내비도 운전자 승인 뒤 생긴 추가·제거 요청에 시연자가 성공·실패·미확인 결과를 지정한다. ‘모의’는 출처이고 성공·실패는 처리 결과이므로 별도로 기록한다. 실제 요청의 결과를 모의 제어로 바꾸거나, 모의 성공을 실제 SDK 완료 증빙으로 사용하지 않는다.

## 6. 이번 목업의 제작 범위

‘필수’는 대표 경험을 완주하기 위해 구현할 항목, ‘추가’는 필수 흐름 완성 뒤 붙일 항목이다. ‘후속’은 이번 기본 제작에 포함하지 않는다. 실제 AI·SDK 연동 결과는 대본 재현과 구분해 기록한다. 아래 기능 ID는 후속 문서에서도 유지한다.

### 6.1. 입력과 시연 데이터의 경계

온보딩은 약 4~6차례의 짧은 채팅으로 재현한다. **자유 텍스트 입력·수정·전송·원문 보존은 필수**이며 선택지는 예시 초안일 뿐이다. 원문은 본인용 웹·서버에서 보존하고 상대·차량 전달본에는 넣지 않는다. 준비된 후속 질문은 질문 차례에 따라 이어지며 입력 내용을 AI로 분석한 결과로 설명하지 않는다.

요약에서는 본인이 쓴 답변을 그대로 다시 확인할 수 있다. 소개에 사용할 지원 관심사·대화/여행 성향·표현은 별도 확인 카드에서 본인이 선택·수정·확인한 값만 저장한다. 준비된 소개 예시를 쓰지 않고 미확인 항목을 비워둔 채 최소 소개나 본인 여행으로 계속할 수 있다. 자유 답변을 임의의 프리셋으로 치환하거나 예시 답변으로 다시 보내도록 강제하지 않는다. 실제 자유 대화 분석·말투 자동 추론은 후속이며, 원문 입력을 받는 기능과 구분한다.

대표 여행의 권역·날짜·시간·경로·후보·만남 장소는 고정한다. 대표 소개용 구조화 값은 바다 산책·카페, 여유로운 여행·조용한 대화, 차분하게·가벼운 농담이다. 그 밖의 자유 답변도 입력·저장할 수 있지만 자동 분류하지 않는다. 본인이 확인하지 않은 구조화 값은 비워두고 중립 대사·일정 중심 추천을 사용한다. 소개 공개를 보류해도 본인 여행을 유지한다. 자유 여행 검색이나 임의 조건에 대한 실시간 추천은 후속 범위다.

이번 목업은 한 회차에 상대 연결 요청 한 건을 진행한다. 요청 거절·취소·연결 종료 뒤에는 본인 여행을 이어가고, 새 연결·요청 이후의 프로필/계획 재설정은 O01의 전체 초기화로 시작한다. 공개 철회는 연결 종료 뒤 가능하지만 새 연결 자격을 되살리지 않는다. 최종 선택 재시연만 같은 이야기의 선택 직전 맥락을 복원한다. 여러 상대 재탐색·반복 연결은 이번 범위에 추가하지 않는다.

## 7. 구현 방향과 제작 완료 기준

### 7.1. 구현 방향

- **웹:** 모바일 폭의 HTML·CSS·JavaScript 목업을 기본으로 한다. 기존 시안 활용 범위는 03번 화면 설계와 대조해 정한다.
- **차량:** Android Studio·Kotlin으로 앱을 만들고 Pleos Connect Emulator에서 실행한다. 공식 시작 가이드는 Android SDK API 34와 최소 SDK API 28 이상을 안내한다. [개발 시작 안내](https://document.pleos.ai/docs/pleos-only/getting-started)
- **웹과 차량 연결:** 시연 PC의 공통 전달 서버에 웹 선택 결과를 저장하고 차량 앱이 불러오는 방식을 기본안으로 둔다. 여행 ID·상태 버전·공개 프로필과 본인 일정의 경계를 맞춘다. 서버·주소·호출 형식은 04번에서 확정하며 운영 계정 서버·DB는 후속이다.
- **에이전트 표현:** 이번에는 대본·표현 프리셋·추천 근거 데이터로 재현한다. 공개 프로필 기반 소개, 사용자 메시지 전달, MC 발화를 구분한다. 실제 추론·자동 실행을 구현한 범위만 별도 기록한다.
- **내비 연동:** NaviHelper의 경유지 요청과 결과 확인을 우선 검증한다. 취소 시 경유지 제거, 원래 여정 유지 여부, 실패 처리를 함께 확인한다. SDK 버전·지원 API·시험 좌표·성공 증빙은 04번에 기록한다. [NaviHelper 안내](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/NaviHelper/intro)
- **음성과 위치:** 준비된 음성과 자막을 기본으로 한다. 2026년 11월 10일 확인한 공개 프로젝트 안내에서 FusedLocation·TextToSpeech·SpeechToText는 준비 중으로 표시되어 있다. 실제 팀 프로젝트의 지원·권한 상태를 확인한 뒤 연동 여부를 정한다. [SDK 사용 상태 안내](https://document.pleos.ai/docs/pleos-only/create-my-project)

### 7.2. 이동 중 경험과 주행 제한

**이동 중 상대 캐릭터와 음성으로 알아가는 경험은 서비스의 핵심으로 유지한다.** 주행 중이라는 이유만으로 음성 문답까지 일괄 금지된 것으로 설명하지 않는다. Pleos UI 가이드는 핸즈프리 음성 인터랙션을 다루지만, 우리 앱의 카테고리·DO·지역/차종·실제 제한·마이크/오디오 지원이 승인·검증됐다는 뜻은 아니다. [음성 인터랙션 가이드](https://document.pleos.ai/docs/connect/guide/docs-design/Introduction/intro), [앱 카테고리](https://document.pleos.ai/docs/pleos-only/vehicle-app-planning-guide/app-category)

| 모드 | 설계·제공 범위 |
|---|---|
| `parked` 주차 | 큰 캐릭터·대화/장소 목록·동의·메시지 전송·내비 승인·최종 선택 |
| `driving_voice` 주행 중 음성 대화 목표 | 지원이 검증된 경우 상대 캐릭터와 짧은 음성 문답·쉬기·종료. 목록·키보드·긴 자막·큰 애니메이션·새 전송/동의/내비 변경은 열지 않음 |
| `blocked` 플랫폼 차단·지원 미확인 | 재생·수집 중단, 표시가 허용되면 최소 안내. 플랫폼이 앱을 가리면 따름. 실제 제한 우회 금지 |

주행 음성 모드는 기본 경험의 목표 설계다. 실제 제공은 유효한 지원 증빙·DO/카테고리 조건·현재 CarUxRestrictions와 기능별 허용·fresh 차량 상태·foreground·마이크 권한·오디오 포커스가 모두 확인된 환경으로 한정한다. DO 선언만으로 허용하지 않으며 속도 0·신호 대기만으로 주차 모드를 열지 않는다. 현재 구현과 미검증 환경은 blocked가 기본이다. 세 모드는 03·04·08의 같은 이름을 사용한다.

목업은 주차 또는 별도 발표 자료에서 준비된 사용자 대사·캐릭터 음성으로 이 흐름을 재현한다. 실제 STT·자유 발화 해석·실주행 지원을 완료했다고 표시하지 않고 마이크가 실제 열리지 않았는데 ‘듣는 중’으로 꾸미지 않는다. 사용자 무응답을 재촉하지 않고 ‘잠깐 쉬자/대화 그만’과 내비·안전 안내에 따른 중단을 제공한다. 음성으로 새 메시지 전송·통화·만남 동의·경로 변경을 실행하는 것은 이번 목업에 추가하지 않는다.

공개 STT/TTS API 문서와 실제 SDK 신청·사용 가능 상태를 구분한다. 2026-11-11 공개 프로젝트 안내에는 SpeechToText·TextToSpeech가 준비 중으로 표시되어 있어 프로젝트 콘솔·제공 SDK·차종별 검증이 필요하다. Gleo의 앱 기능 호출 연동도 캐릭터의 자유 대화를 자동 제공하거나 승인하는 기능으로 설명하지 않는다. [SDK 상태](https://document.pleos.ai/docs/pleos-only/create-my-project), [Gleo Interface](https://document.pleos.ai/docs/pleos-only/app-integration-guide/guide/core-concepts)

실제 지원 판정과 근거는 04번 7절·05번 V05에 기록한다. 내비·안전 안내에 대한 포커스 상실/감쇄를 따르고 복귀 시 대화·사용자 명령을 자동 재실행하지 않는다. [주행 규제 개발](https://document.pleos.ai/docs/pleos-only/vehicle-app-developer-guide/driving-restriction-development-guide), [오디오 포커스](https://document.pleos.ai/docs/pleos-only/vehicle-app-developer-guide/audio-focus-development-guide/audio-focus-development)

### 7.3. 시연 초기화 기준

- **처음부터 시작:** 온보딩 답변·공개 승인·선택값·여행·연결·만남·최종 선택·B 이벤트·미처리 응답을 웹·서버·차량에서 초기화한다. 새 시연의 상태를 이전 응답이 변경하지 않도록 한다.
- **최종 선택 재시연:** 만남이 종료되고 최종 선택하기 직전의 이야기 맥락을 유지하며, 양쪽 최종 선택과 이후 결과만 초기화한다. 현재 내비·제한·복구 기록은 과거 값으로 되돌리지 않는다. 함께하는 결말의 선택이 다음 결말에 남지 않게 한다.
- **외부 내비 상태:** 앱 초기화가 실제 내비 경로까지 자동 초기화한다고 가정하지 않는다. 시연 전에 시험 경로·경유지 상태를 확인하고, 필요한 제거·복원과 결과 확인 절차를 04번에 둔다.

### 7.4. 완료를 판단하는 기준

1. 웹에서 폼 설문을 나열하는 대신 에이전트 질문·답변·요약·공개 승인으로 프로필을 준비하고, 지원하는 변경값이 소개와 차량에 반영된다.
2. 여행 계획 저장 뒤 에이전트가 후보를 제안하며 공통 관심사·시간·이동 부담을 설명한다. 표시값은 시연 데이터와 일치한다.
3. 웹의 프로필·여행·연결 정보가 차량 앱에 동일하게 표시된다. 불러오기 실패와 재시도를 제공한다.
4. 상대 캐릭터와의 대화, 직접 확인한 말 전달, B의 응답을 구분해 진행할 수 있다. 캐릭터 답변을 실제 상대의 실시간 발언으로 표시하지 않는다.
5. 콘텐츠를 선택·종료·건너뛸 수 있다. 통화는 양쪽 동의 후 시작하고, MC가 없거나 거절되어도 일반 통화와 만남 제안이 막히지 않는다.
6. 만남 장소의 추천 이유와 양쪽 일정 충족 여부를 확인하고, 동일 제안에 대한 양쪽 동의와 내비 승인을 별도로 진행할 수 있다. 취소 전후와 실패 상태를 구분한다.
7. 사람과 함께하는 결말과 내 캐릭터와 이어가는 결말을 모두 완주한다. 후자에는 온보딩 취향을 활용한 대화와 다음 활동이 있고, 이유 입력 없이 진행할 수 있다.
8. 주행 제한 상태에서는 제한 대상 입력·선택·승인을 실행할 수 없다. 실제 플랫폼 동작을 검수하고 이동 구간의 개념 시연과 구분한다.
9. 전체 초기화와 최종 선택 재시연을 구분하고, 이전 이벤트·선택이 새 시연이나 다른 결말에 섞이지 않는다.
10. 실제 AI·SDK 호출·성공·실패 증빙과 재현 화면을 구분한다. SDK 검증 실패 시 재현으로 이야기는 완주하되 해당 연동은 미완료로 기록한다. 차량 앱의 에뮬레이터 실행 자체는 필수다.

전체 화면을 만들기 전에 저장한 공개 프로필·캐릭터 선택값 한 건을 에뮬레이터에서 불러오는 연결을 먼저 확인한다. 차량 담당은 NaviHelper 초기 호출과 주행 제한·오디오 동작 확인을 병행한다. 정확한 담당·기한은 05번에서 정한다.

## 8. 결정 사항과 후속 문서

### 8.1. 이번 개정에서 적용하는 기준

기존 모바일·Pleos 초안과 범위 정의서 v0.1을 바탕으로 다음 방향을 반영한다. 이번 목업의 제작 범위는 이 문서를 기준으로 하며, 기존 초안과 다른 항목은 아래 기준을 적용한다.

- 온보딩을 대화형으로 바꾸고, 사용자 확인을 거친 관심사·표현 스타일과 캐릭터 소개를 연결한다.
- 여행 계획 이후 후보 비교는 유지하면서, 에이전트가 먼저 추천하고 이유를 설명하는 흐름을 강화한다.
- 차량 대화의 목적을 이동 시간에 서로 익숙해지는 경험으로 명시한다. 상대 캐릭터 대화·말 전달·직접 통화·MC 통화를 선택 가능한 콘텐츠로 구분한다.
- 실제 주행 지원은 별도 검증하고, 목업의 주차 중 조작과 이동 구간 개념 시연을 구분한다.
- 만남 장소를 에이전트가 두 사람의 경로·일정·취향을 바탕으로 제안한다. 실제 검색·계산은 후속이며 이번에는 가상 장소 한 곳을 사용한다.
- 두 결말을 함께 여행하기와 내 캐릭터와 여행하기로 구성한다. 내 캐릭터는 온보딩부터 이어지는 친구로서 각자 여행의 결말에도 구체적인 경험을 제공한다.
- 대화 연결·콘텐츠 동의·만남 확정·내비 승인·최종 동행을 구분한다. 취소와 경로 변경, 전체 초기화와 결말 재시연도 구분한다.
- 출발지 탐색 확대·점수 공식·실제 생성형 AI·음성 특징 분석·실제 통신은 후속 설계로 보존한다.
