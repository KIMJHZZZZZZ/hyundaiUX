0. Executive Summary
현재의 핵심 문제는 아이디어 부족이 아니라 선택 기준의 혼선이다. 기존 연구는 폭넓게 수행됐으나, 정서적으로 좋은 장면·실질 손실이 큰 문제·자동차에서만 발생하는 문제·앱으로 실제 바꿀 수 있는 결과를 혼용했다. ’창밖동화’의 강점은 감성 자체가 아니라, 부모가 실제로 반복하던 행동과 이동 경로·차창의 변화가 맞물리는 경험을 발견했다는 점이다.
제안하는 제품화 원칙은 ’차량 상태 → 사용자 선택 → 변화된 결과’의 폐회로이다. 예를 들어 충전 중 SOC가 바뀌면 밤새 공조를 사용할 계획도 변해야 한다. 주소 도착 후 실제 업무가 남는 경우, 차량 정차와 작업 완료를 구분해야 한다. 반대로 개인정보를 삭제할 권한이 없는 앱이 ’한 번에 차량 기록 삭제’를 주장해서는 안 된다.
우선 검증 트랙을 2개로 분리한다.
실질 문제 해결 트랙: NightReserve(차박 에너지), WorkStop(업무 목적지의 마지막 100m), ChargeRecovery(충전 실패 뒤 복구), BorrowSession(차량 교대·반납).
새로운 차량 경험 트랙: ChargeQuest(충전 중 차량 상태와 연동되는 가족 참여형 게임), 맥락형 Gleo 개인 비서의 특정 전문 영역. 게임·반려 캐릭터 자체는 테슬라와 현대차 기존 아이디어에 이미 있으므로 소재가 아닌 새 경험·행동·데이터 연결을 검증한다.
메인 시연 후보는 NightReserve를 우선 제안하되 확정하지 않는다. 차량 SOC·공조·주행 가능 거리의 연계가 화면에서 직관적으로 보이고 Virtual Console로 상태를 재현할 수 있기 때문이다. 다만 기존 전기차 Utility/Camp 모드와 차별성이 입증되지 않거나 에너지 소모 예측이 부정확하면 신속히 다른 후보로 교체한다. 시연 수치는 모두 가상 데이터이며 안전한 주행 가능 거리 보증이 아니다.
공모전에서 중요한 것은 같은 앱을 세 매체로 일치시키는 일이다. ① 공식 접수양식(기획서)의 문제 정의, ② Pleos형 화면과 에뮬레이터 앱, ③ 실제 차량 디자인을 참고한 시연 영상이 동일한 사용자 여정·차량 이벤트·개선 결과를 설명해야 한다.

1.3 제출물 범위

E3 / 공식 검증: 공모전, Pleos SDK, 제조사 기능 명세.

2.3 ’흔한 아이디어’를 피하는 방법
아이디어 개수 목표를 제거한다. 최근에 실제로 문제를 경험한 사람의 마지막 발생 사건을 묻고, 해결을 위해 이미 쓰는 우회 행동(재검색·수동 메모·전화·앱 전환·포기)을 기록한다. 해결 방식을 발상하기 전 차량 SDK의 특정 입력이 없으면 무엇이 달라지지 않는가를 적는다. 앱을 지우더라도 사용자의 행동이 똑같다면 제품 가치가 약하다.

3.2 4개 조사 주제의 함정
(1) 충전 중 게임: 콘텐츠 자체가 해결할 강한 페인포인트는 아닐 수 있다. 긴 대기를 반복하는 이용자를 실제로 찾고, 기존 휴대폰·차량 게임 대비 우위가 있는지 테스트해야 한다.
(2) 차량 다마고치: 현대차 우수작 ’차마고치’와 개념 중복. 상태 읽기→캐릭터 반응만으로는 부족하며, 사용자가 무엇을 더 잘하게 되는지 명확해야 한다.
(3) 페르소나형 비서: Grok·Gleo·범용 음성 비서와 경쟁한다. 범용 비서 대신 특정 책임(차박 전력 계획, 배송 업무 완료, 가족 교대 운행)을 가진 도메인 에이전트가 유리하다.
(4) 자율주행 중 콘텐츠: 자율주행 단계가 실제로 운전자 감독을 면제하는지 확인해야 한다. 현재 감독형 주행 보조 상태의 운전자는 게임·영상 시청 대상이 아니다.

6. HMI 설계: 4:6 메모를 실제 규격과 구분
6.1 검증 결과
설명회 메모의 ’4:6’은 작업 가정으로 보존한다. 그러나 모든 Pleos Connect 화면이 고정 4:6이라는 공식 근거는 확인되지 않았다. 더 뉴 그랜저의 공식 시승 문서는 중앙 17인치 화면을 왼쪽 상태 영역과 오른쪽 앱 영역의 약 1:2 비율로 소개한다. Pleos 설계 문서는 Connect-S(17/14.6/12.9인치), Connect-W, Connect-WF 및 멀티윈도우 정책을 구분한다.

7.1 NightReserve — 밤사이 사용하고 내일 출발하기
가상 장면: 전기차로 차박하는 부부가 오후 10시 주차한다. 배터리가 43%인데 내일 아침 이동에 필요한 여유를 남기면서 밤새 공조를 사용할 수 있을지 모르겠어 여러 화면을 번갈아 본다. 이는 설문으로 확인된 비율이 아니라 제품 실험용 시나리오다.
제품 경험: 사용자는 ’내일 아침 최소로 남기고 싶은 SOC’를 직접 입력하고, 현재 SOC·공조 상태·시간에 따라 보수적 예측 구간을 확인한다. 공조 설정 변경 시 예상 잔량 구간을 즉시 다시 산정한다. P 상태에선 시나리오를 직접 비교하고, 운행 중에는 상세 화면을 닫는다.
차별성 가설: 기존 전기차 Utility/Camp 모드가 전력 사용 자체를 지원한다면, NightReserve는 다음날 출발 계획을 함께 관리한다. 다만 실제 차종의 기본 기능과 기능 비교가 필수다.
MVP: SOC 수집/모의 입력, 공조 상태, 보수적 소비 모델(범위·불확실성 표시), 내일 필요한 여유 SOC 입력, 3개 시나리오 비교, 상태 업데이트. 금지: 주행 가능 거리 보장·정확한 밤샘 잔량 보장·사용자 승인 없는 자동 공조 제어.
결정적 데모: SOC 43→37%, 공조 HIGH→LOW, ’내일 목표 SOC 25%’를 바꿀 때 예측 여유가 달라짐. 성공 지표는 사용자가 출발 전 자신의 계획을 설명할 수 있는지, 기존 기본 화면보다 선택이 빠른지.
7.2 WorkStop — 주소 도착 뒤의 실제 업무
가상 장면: 업무 운전자가 같은 대형 건물을 두 번째 방문한다. 내비 주소는 정문을 가리키지만 물품을 전달할 출입구는 반대편이고, 첫 방문에서 전화·우회로 12분이 걸렸다. 12분은 가상 시연값이다.
제품 경험: 운전자는 첫 방문에서 실제 업무 출입구와 합법적으로 사용할 수 있었던 정차 위치를 본인이 직접 저장한다. 다음 방문에서는 나비게이션의 목적지와 사용자 저장한 업무 도착 지점을 구분해 보여준다. 정차 후 ’전달 완료’를 확인해야 방문 세션이 닫힌다.
MVP: 장소별 사용자 지정 진입점(사진/메모 최소), NaviHelper 목적지/경유지 연계, P 상태 방문 완료, 재방문 복원. 금지: 검증되지 않은 장소를 법적 정차 가능 지점으로 단정.
핵심 반증: 배송 플랫폼/지도 즐겨찾기에 저장해도 동일한 결과라면 차량 앱의 독자성이 없다.
7.3 ChargeRecovery — 실패가 발생한 뒤의 결정
가상 장면: SOC 14%로 도착한 급속충전소에서 결제가 실패한다. 다음 약속까지 45분 남았다. 14%·45분은 데모 값이다.
제품 경험: 사용자가 실패 종류를 선택하면 앱은 현재 SOC와 경로·목적지 제약을 기준으로 여러 대안을 비교한다. 충전소 제휴가 없다면 실제 결제 가능 여부·점유율을 확정하지 않는다.
MVP: 실패 입력, SOC, 남은 일정(수동), 경유지 비교, NaviHelper로 선택 경로 반영. 충전 사업자 서버 연동은 2차 기능.
핵심 반증: OEM EV 경로 계획에 이미 충전 실패 후 동등한 대안이 있다면 차별화 부족.
7.4 BorrowSession — 차량 교대가 끝나는 순간
가상 장면: 직장 동료가 현장 차량을 교대할 때 전 운전자는 ’연료는 충분하다’고 말하지만 다음 사람이 출발 직전 경고등을 발견한다.
제품 경험: P 상태에서 운행 종료 스냅샷(주행거리, 에너지/연료, 표시 가능한 경고·도어)을 남기고, 다음 사용자가 인수 항목을 확인한다. 개인정보를 최소화하고 목적이 끝나면 삭제한다.
MVP: 읽기 권한만 사용, 사용자 확인 체크, 세션 식별자, 상태 비교. 자동 차량 전체 개인정보 삭제·정비 진단 주장 금지.
핵심 반증: 기존 차량 관리 SaaS와 동일한 비용·사용 흐름이면 차별성 낮음. 중소 규모 단기 공동 차량에 특화할지 검증.
7.5 ChargeQuest — 충전기가 만드는 미니 공동 게임
가상 장면: 급속 충전 중 20분가량 대기하는 가족이 차 안에서 함께 놀고 싶다. 사용자는 이미 스마트폰 게임이 있지만 ’충전이라는 사건’과 게임이 결합되면 참여가 달라지는지 알고 싶다.
제품 경험: P 상태에서 시작하는 간단한 협력 퍼즐. 단계는 실제 SOC 구간 변화·충전 상태 이벤트와 연동하며, 충전이 중단되면 자동으로 일시정지한다. 게임을 위해 충전을 지연하거나 운전자 주의가 분산되면 안 된다.
MVP: 미니 퍼즐 1종, SOC 이벤트, 2인 교대 입력, 안전 종료. 독창성은 ’차량 다마고치/Arcade’와 다른 사용자 행동에서만 주장한다.
핵심 반증: 일반 태블릿 게임만큼만 재미있고 차량 정보는 장식이라면 유망 후보가 아니다.

8.2 사업성 수치 제시 규칙
첫 버전에서 ’예상 MAU 10만’처럼 근거 없는 값을 만들지 않는다. 대신 가설을 계산 구조로 정의한다. 초기 도달 가능 이용자 = 대상 차종 운전자 × 해당 상황 경험 비율 × 설치 전환율, 월간 활성 이용자 = 설치자 × 월간 사용 사건 발생률 × 유효 사용률로 구분하고 각 항의 출처·측정 방법을 명시한다. 사건이 적은 서비스는 월간 활성 대신 ’발생한 문제의 완료율’을 주지표로 둘 수 있다.

9. 실제 현대차 디자인 기반 목업 전략
9.1 차량·이미지 선정 기준
더 뉴 그랜저(2026)를 우선 차량 레퍼런스로 선정한다. 17인치 Pleos Connect 중앙 화면과 9.9인치 슬림 디스플레이가 공식 발표됐으며, 실제 콕핏 이미지·UI 자료가 공개돼 있다. EV 전용 NightReserve를 이 그랜저에 그대로 탑재한 것처럼 보이면 잘못된 차종 적용으로 오해될 수 있으므로, EV 데모는 브랜드 중립 Pleos 개념 콕핏으로 우선 시연하고 EV 공식 적용 차종의 실제 제공 기능·형상을 별도 확인한 뒤 합성한다.
메인 HMI 시안의 스크린샷은 공식 디자인 자료를 참고한 비공식 컨셉 UI로 제작한다. ’실차 촬영’이나 ’현대차 승인 UI’로 표기하지 않는다. 실제 공개 사진의 무단 재배포 여부가 명확하지 않으면 최종 제출물에는 사진 대신 자체 제작 콕핏 구조도와 출처 링크를 사용한다.

10. 개발 전략과 범위
10.1 MVP 구조
VehicleAdapter(실SDK/Mock 공통 인터페이스) → VehicleStateStore(SOC/HVAC/P, 시간 기록) → ScenarioPlanner(사용자 입력·보수적 상태 모델) → UI(portrait/landscape, Drive/P) → EventLog(재현 가능한 테스트 결과).
외부 로그인·결제·커뮤니티·대규모 콘텐츠 생성은 1차 MVP 필수 기능에 포함하지 않는다. SDK가 없더라도 모의 데이터로 제품 가설을 검증할 수 있지만, 모의 데이터 시연은 SDK의 실제 호출 성공과 구분한다.
